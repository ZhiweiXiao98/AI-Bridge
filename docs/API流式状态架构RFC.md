# API 流式状态架构 RFC

> 复核日期：2026-09-26。本文保留后续状态、投影与渲染的设计约束；现有实现见[结构化消息与调度](API模式结构化协议与调度引擎重构计划.md)。

## 现有边界

API 流事件由 `app/core/api/` 产生，经 Worker 流桥接与上游 consumer 传递到客户端。聊天页面协调回合状态、历史消息和流式展示；会话存储与请求快照提供持久化内容。

## 设计约束

1. 每个事件明确所属会话、请求、回合和流；接收端核对目标。
2. 正文、thinking、工具调用和工具结果各自保持结构与身份。
3. 状态变化由事件驱动，渲染依照可检查的状态投影执行。
4. 流结束、工具执行和回合结束采用明确的不同语义。
5. 重复、延迟和乱序事件具备明确处理规则。
6. 取消、切换会话、重连和重载均有可验证的最终状态。

## 后续评估

- 统一事件身份、版本、排序与去重规则，并评估 RPC 兼容范围。
- 明确状态存储、投影和渲染的接口，降低页面协调逻辑的耦合。
- 建立可回放的事件样本，用于复现流式与工具时序问题。
- 以实际长回复、thinking 和多轮工具调用评估渲染性能。

以上条目属于设计与验收要求，实施范围需结合现有调用链确定。具体检查见[API 回归清单](API模式回合状态机改造回归测试清单.md)。

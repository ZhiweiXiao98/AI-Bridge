# 一、背景与目标

API 模式与浏览器模式下，工具调用展示曾存在"调用与结果没有稳定绑定"的问题：

- **API 模式**：天然结构化基础（`tool_call` / `tool_result` segment），适合围绕 `tool_call_id` 强绑定
- **浏览器模式**：结果经 worker 执行后作为文本回流浏览器，再由 parser 提取拆分，链路更长

浏览器模式真实链路：
```
AI 网页输出 tool_call → worker 抓取本地执行 → V2 协议文本发回浏览器
→ parser 拆分为 tool_result → UI 渲染
```

**目标**：将双模式工具调用展示从"聚合文本/普通文本回流"升级为"可解析、可绑定、可观察的工具卡片模型"。

**核心原则**：

| 原则 | 说明 |
|------|------|
| 不用顺序绑定 | 依靠 `tool_call_id` 而非位置对应 |
| 本地生成 `tool_call_id` | 格式 `toolcall_<uuid4_hex_8>`，不依赖 AI 输出 id |
| 只有被 runtime 接纳的调用才进绑定链 | 解析失败/协议非法的块仅作普通文本展示 |
| `ToolResultBox` 只承载结果 | 运行中状态由独立 `ToolCallCard` 承载 |
| 双模式统一模型，允许解析路径不同 | 最终收敛为统一结构 |
| 任务面板事件驱动为主，轮询兜底 | 短任务生命周期可能短于轮询周期 |

## 阶段 I：浏览器模式状态机治理 ✅

### 背景

`_browser_round_state` 散落在 `worker.py` 的 5 个方法中，共 10 处直接赋值，无统一转换表、无守卫、轮询线程与 executor 线程可能竞争。所有后续功能（运行中状态绑定、取消回填、UI 状态显示）都依赖状态机可靠性。

### 现状（10 处赋值分布）

| 方法 | 设置的状态 | 触发条件 |
|------|-----------|----------|
| `__init__` | `idle` | 初始化 |
| `_browser_detect_state` | `ai_streaming` / `processing` | 轮询检测 busy→idle 转换 |
| `_background_process_ai_response` | `fixing` → finally `idle` | 主流水线 |
| `_background_process_ai_response_direct` | finally `idle` | 兜底流水线 |
| `_check_and_handle_tool` | `tool_executing` → `system_sending` → finally `idle` | 工具执行链 |

问题：
- 没有转换表，任何地方都能覆盖
- `_browser_detect_state`（轮询线程）和流水线 finally（executor 线程）可能竞争
- `_update_ai_state` 是 UI 侧状态的独立信号，和 `_browser_round_state` 是两套东西但经常一起设置
- `system_sending` 保护逻辑靠 `if != "system_sending"` 硬编码守卫

### 目标

提取独立模块 `app/core/round_state/`，将散落的状态赋值收口为事件驱动的统一状态机。

### 文件结构

```
app/core/round_state/
├── __init__.py                  # 导出
├── round_state_machine.py       # 状态机核心：状态枚举、转换表、守卫
├── round_state_events.py        # 事件枚举
└── round_state_models.py        # RoundStateSnapshot 数据模型
```

### 状态定义（浏览器模式）

```
idle            # 空闲
ai_streaming    # AI 正在生成回复
processing      # AI 回复结束，正在处理输出
fixing          # 流水线执行中（AutoFix 等）
tool_executing  # 工具正在执行
system_sending  # 工具结果发回网页
```

### 合法转换表

```
idle → ai_streaming          (检测到 busy)
idle → tool_executing        (事件驱动工具触发)
ai_streaming → processing    (busy→idle 转换)
processing → fixing          (流水线启动)
fixing → idle                (流水线结束，无工具)
fixing → tool_executing      (流水线中检测到工具)
tool_executing → system_sending  (工具结果发回)
tool_executing → idle        (工具执行失败/无结果)
system_sending → ai_streaming    (等待 AI 回复)
system_sending → idle        (超时/异常)
* → idle                     (ERROR 事件，任何状态可回 idle)
```

非法转换打 WARNING 日志但不阻断执行（避免卡死）。

### 实施步骤### 浏览器 loop 阻塞分析

当前浏览器主循环存在三个阻塞点：

| 阻塞点 | 位置 | 影响 |
|--------|------|------|
| `_execute_task(task)` 同步执行 + `sleep(1.0)` | `_browser_detect_state()` 末尾 | 轮询循环被任务执行卡住 1s+，状态刷新延迟 |
| `_check_and_handle_tool()` 同步调用 | `_background_process_ai_response()` 内部 | 工具执行链阻塞流水线线程，期间无法检测新状态 |
| `_check_and_handle_tool()` 长链路 | 自身 | 工具识别+执行+结果构造全在一个同步调用中，影响消息扫描和状态刷新 |

改造目标：检测层只负责识别与投递，执行层走独立后台任务，轮询循环不被阻塞。

### 实施步骤

| 步骤 | 内容 | 状态 |
|------|------|------|
| [√] 1 | 创建 `app/core/round_state/` 模块四个文件 | ✅ |
| [√] 2 | 实现状态枚举、事件枚举、转换表、守卫 | ✅ |
| [√] 3 | Worker `__init__` 实例化状态机，添加 import | ✅ |
| [√] 4 | 替换 10 处 `_browser_round_state` 直接赋值为 `handle_event()` 调用 | ✅ |
| [√] 5 | `_update_ai_state` 改为订阅状态变更回调（`_on_round_state_change`），不再手动同步 | ✅ |
| [√] 6 | 状态变更日志：每次转换输出 `old → new (event)`（已内置于状态机） | ✅ |
| [√] 7 | `_browser_detect_state()` 中 `_execute_task()` 改为 `executor.submit()` 异步投递 | ✅ |

| [√] 10 | 验证：正常对话、工具执行（knowledge_search/web_search）、流水线、idle 穿插，零非法转换 WARNING | ✅ |

### 设计原则

- 第一步只做浏览器模式，API 模式暂不动（目前只有 busy/idle 两态，无治理紧迫性）
- 状态机不直接被外部赋值，通过 `handle_event(event)` 触发转换
- 非法转换不阻断，打 WARNING 日志
- 线程安全：内部用 `threading.Lock` 保护状态读写
- `_update_ai_state` 作为状态变更的下游回调，不再是独立的手动调用
- 检测层（轮询线程）只做状态识别和事件投递，不做同步执行
- 执行层（executor 线程池）负责工具执行、任务执行等耗时操作
- 保留旧链路兜底：异步化后如果 executor 满载，降级为同步执行并打 WARNING

# 四、已实现的跨阶段修复

## 4.1 跨消息绑定空气泡修复 ✅

浏览器模式下，`_try_cross_message_tool_binding` 隐藏 `ToolResultBox` 后，User 气泡只剩 header 变成空气泡。

三层防御：
1. text segment 空内容跳过渲染
2. `update_content` 末尾检查 `c_layout.count()`
3. `_hide_bubble_if_empty()` 在跨消息绑定后检查气泡可见性

## 4.2 流水线状态间隙消除 ✅

主/兜底流水线 finally 检查 `_browser_round_state != "system_sending"` 才恢复 idle，避免工具结果发送 → AI 回复之间出现 idle 间隙。流水线入口设置 `fixing` 状态，AutoFix 期间阻止用户直接发送。

## 4.3 V2 协议 HTML 标签剥离修复 ✅

浏览器 DOM 中 V2 协议文本被 `<p class="user-text">` 包裹，`parser.process_rich_text()` 进一步包为 `<p>[TOOL_RESULTS_BEGIN...`，导致 `startswith` 不命中。

修复：`_split_tool_feedback_text_segment()` 在 `startswith` 检查前用正则剥离外层 HTML 标签。V1 和 V2 两条路径均受益。

## 4.4 浏览器模式角色判定修复 ✅

`message_area._render_next_slice()` 原用 `current_render_idx % 2 == 0` 奇偶位置猜测角色，在工具回显消息、连续 AI 消息等场景下角色全部错位，直接影响跨消息绑定。

修复：改为 `msg_data.get('role') == 'User'`，使用 Driver 层已基于 `data-message-ai` DOM 属性准确判定的 role 字段。为跨消息绑定提供了正确的角色基础。

## 4.5 hold-render 机制

`page.py` 的 hold-render 在 `running_tools` 状态下阻止 UI 重绘。API 模式已通过增量更新绕过（状态栏走独立信号）；浏览器模式待推进。

# 六、风险与边界

1. **不使用顺序绑定** — 容易藏问题，返工成本更高
2. **浏览器旧文本兼容** — 旧数据含非标准 `tool_call` / 聚合字符串，改动必须控制边界
3. **取消不能只做 UI 假动作** — `cancel_requested` ≠ `cancelled`，底层必须配合
4. **向后兼容** — 旧消息无 `tool_call_id` 走 `ToolResultBox` 旧路径，不做数据迁移
5. **不把 knowledge_search 特判当最终方案** — 所有短生命周期工具都可能被轮询错过

背景 & 目标

当前建议助手已经打通基础链路：接收输入 → LLM 生成 → 输出建议。 现阶段已完成的核心修复包括回复上下文补充、Daemon 桥接兼容、SuggestTask 上下文整合等。

现在的问题不再是"能不能跑"，而是 "能不能更像用户、更懂用户、更稳定"。

演进目标
✅ 更像用户的表达方式
✅ 更懂当前对话意图
✅ 更少泛化建议
✅ 更稳定地处理长上下文
✅ 更容易通过数据验证效果

Phase 1 · 近期落地 ▼
记忆与人设系统
让建议助手表现出"这个人就是这么说话"的感觉，而不是每次都像一个无记忆的新模型。

关键能力

  • 会话记忆：保留当前会话最近对话和意图
  • 长期风格记忆：记录常用口头禅、常见句式、禁用表达、偏好语气
  • 反馈记忆：记录哪些建议被采纳、修改、忽略

三层设计

💬
短期上下文
当前对话内容、最近几轮、当前意图
📝
长期风格记忆
常用表达、禁用词、语气偏好
📊
行为反馈记忆
点击、拖拽、采纳、忽略

验证标准

建议语气是否逐步接近用户习惯 是否减少了空泛句式 是否更少出现低信息建议
Phase 2 · 近期落地 ▼
上下文折叠与 token 控制
让建议助手在长对话、长群聊、长邮件链场景下依然稳定运行，不出现上下文污染或 token 爆炸。

关键能力

  • 微压缩：去掉寒暄、重复系统消息、无效噪声
  • 滑动窗口：保留最近 N 轮完整原文
  • 摘要折叠：把更早历史折叠成结构化摘要
  • Prompt Cache：把长期不变的风格部分做缓存化管理

推荐折叠结构

✅ 保留（最近窗口）

最近 N 轮完整原文
当前用户输入
当前意图标注

📦 折叠（更早历史）

事实摘要
意图摘要
风格摘要

验证标准

长对话下建议是否还能保持稳定 token 消耗是否可控 是否出现明显的历史噪声干扰
Phase 3 · 近期落地 ▼
反馈闭环
让建议助手不是"只生成"，而是"会学习什么建议有用"。

关键能力

  • 记录建议是否被点击
  • 记录建议是否被拖拽到输入框
  • 记录建议是否被直接发送或二次修改
  • 统计不同模式下的采纳率

Phase 4 · 后续升级 ▼
MCP 检索能力
让建议助手不仅"像你说话"，还能在必要时"查清事实后再说"。

适用场景

  • 涉及代码状态
  • 涉及项目进展
  • 涉及文档内容
  • 涉及外部系统状态

建议方式

  • 以工具插件方式接入检索能力
  • 当检测到需要查证的场景时，后台拉取事实
  • 再结合用户风格生成建议

⚠️ 风险提示

系统复杂度上升 工具链路变长 需要严格控制失败降级
Phase 5 · 后续升级 ▼
多 Agent / 投机执行
把复杂任务拆给多个角色处理，提高候选质量和响应速度。

可选角色分工

  • 研究员：负责查资料和事实
  • 打字员：负责按用户风格生成文本
  • 审核员：负责检查风险和一致性

适用范围

适合高价值、强审查、复杂事实查证场景；不建议作为当前阶段的默认路径。

⚠️ 风险提示

架构成本高 调试困难 容易过度设计

推荐实施顺序

🟢 近期

  • 做长期风格记忆
  • 做上下文折叠
  • 做建议反馈闭环

🟡 中期

  • 做模式区分优化（browser / API 分风格）
  • 做建议去重与意图分层
  • 做低置信度静默策略

🔵 长期

  • 接入 MCP 检索
  • 引入多 Agent 协作
  • 做投机执行与预判草稿

✅ 验收标准（第一阶段目标达成）

建议内容不再明显泛化
建议语气更贴近用户风格
建议在长上下文中仍能保持稳定
可通过点击率 / 拖拽率 / 采纳率判断优化效果

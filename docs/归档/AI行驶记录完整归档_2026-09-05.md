## 高价值踩坑记忆

- 浏览器模式纯文本工具协议中，不要在外层 `tool_call` 代码块内部再嵌套三反引号代码块；这会提前闭合外层围栏，导致工具路由解析不到意图。
- RemoteWorker 架构下，客户端即使在本机也常走 WebSocket RPC；不要假设 UI 进程持有服务端 `DockerManager`、`FileService` 或工具运行实例。

## 2026-06-20 | RemoteWorker 信号协议收敛与漏接治理 | ✅ 已解决

- **标签**: `remote_worker` `signal_protocol` `websocket` `api_mode` `testing`

#### 1. 用户原始诉求
用户指出当前架构通信有问题，无法做好信号管理，尤其是 `RemoteWorker` 会让大量 agent 陷入前后端联调。

#### 2. 背景与上下文
远程模式下，UI 进程并不直接持有服务端 `WorkerThread`，而是经由 WebSocket RPC 和 HTTP 拉取同步状态。此前同一个事件需要在 `WorkerThread` 信号定义、`server.SignalBridge`、`RemoteWorker.on_agent_msg`、UI 连接处多点手工维护。任何一处漏接，remote 模式就会表现为“后端似乎没发”或“前端似乎没接”，导致联调成本被放大。

#### 3. 目标
1. 收敛服务端信号到远程消息的映射。
2. 收敛远程消息到客户端 Qt 信号的映射。
3. 补齐 API 模式和上下文工作台高频漏接信号。
4. 用测试约束后续新增 signal 时必须补齐 remote 链路。

#### 4. 实施方案
- 新增 `app/core/remote_protocol.py`，集中声明 `SERVER_SIGNAL_ROUTES` 和 `REMOTE_MESSAGE_ROUTES`。
- `server.SignalBridge` 保留 `messages/sessions/ota` 的通知后 HTTP 拉取特殊通道，其它普通信号改为按 registry 自动绑定。
- `RemoteWorker.on_agent_msg` 保留通知拉取、OTA 和状态副作用，其它消息统一交给 `REMOTE_MESSAGE_ROUTES` 分发。
- 给 `RemoteWorker` 补上 `api_manual_compact_signal`。
- 补齐 `context_status`、`api_messages_deleted`、`api_manual_compact`、`mode_changed`、`skills_data`、`system_prompt`、`subagent_suggestion`、`daemon_suggestion` 等 remote 路由。
- 顺手修复 `WorkerSkillsBridge.get_system_prompt()` 对旧式 `generate_system_prompt()` fake/实现的兼容：支持新版 `{content, summary}`，不支持 `summary_only` 时退回旧字符串 payload。

#### 5. 关键改动文件
- `app/core/remote_protocol.py`
- `app/core/remote_worker.py`
- `server.py`
- `app/core/worker_modules/worker_skills.py`
- `tests/test_remote_protocol.py`
- `AI_JOURNAL.md`

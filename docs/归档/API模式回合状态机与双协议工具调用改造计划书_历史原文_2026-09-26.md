# API模式回合状态机与双协议工具调用改造计划书

> 最后编辑时间：2026-04-18
> 状态：阶段 A、B、C、D、E 代码完成；运行实测待补
> 适用范围：API 模式、流式输出、工具执行闭环、原生 FC / Markdown `tool_call` 共存改造
> 用途：用于指导 AI 或工程师按阶段、有顺序地实施改造，避免局部修补导致架构进一步失控。

***

# 一、背景

当前 API 模式已经具备以下能力：

- 首轮 assistant 文本流式输出
- 工具闭环（tool loop）
- `tool_feedback` 作为结构化 assistant 消息回填
- UI 端流式临时气泡与全量历史重绘
- 新旧工具链并存：`tool_runtime` 主链 + Markdown/正则兼容链

但目前存在一个核心问题：

**UI 状态机与后端回合状态机严重脱节。**

当前系统大致只区分：

- 正在流式
- 流式结束

但真实业务状态至少包括：

- 首轮 assistant 流式回复
- 工具检测
- 工具执行
- followup 生成
- 整轮最终完成

这会导致以下问题：

- 流式结束后 UI 误以为整轮完成，过早重绘正式消息
- `tool_feedback` 与 followup 追加进 history 后，与流式临时气泡产生冲突
- UI 无法正确表达“正在执行工具中”的状态，容易给用户造成卡死感
- 若后续直接接入原生 FC（Native Function Calling），将进一步加剧时序混乱

因此，本计划书的结论是：

**必须先重构 API 回合状态机，再推进原生 FC 与 Markdown** **`tool_call`** **共存。**

***

# 二、目标

本计划分两个层级目标：

## 2.1 第一层目标：先解决当前流式与工具执行冲突

建立统一的 API 单回合状态机，让以下链路解耦：

- 首轮 assistant 流式输出
- 工具检测与执行
- followup 生成
- UI 正式消息接管

## 2.2 第二层目标：为双协议工具调用共存打基础

在不立即大规模重写的前提下，为后续接入以下能力预留稳定结构：

- 原生 FC（Native Function Calling）
- Markdown 围栏 `tool_call`
- legacy `# EXEC` 代码块执行

并形成统一工具候选池与协议优先级选择机制。

***

# 三、核心设计原则

## 3.1 先重构状态机，再扩工具协议

不允许跳过状态机直接接原生 FC，否则会继续出现：

- UI 错位
- 流式与工具回填互相打架
- 历史消息结构混乱
- 调试快照不可读

## 3.2 单轮只执行一种最终工具协议

第一阶段不做“同一轮同时执行原生 FC 和 Markdown `tool_call`”。

推荐优先级：

```md
native_fc > markdown_tool_call > legacy_exec_code
```

即：

- 如果本轮命中原生 FC，则优先执行原生 FC
- 否则回退 Markdown 围栏 `tool_call`
- 再否则回退 legacy `# EXEC` 代码块执行

## 3.3 状态机应支持循环，而不是一次性线性流程

真实 Agent 回合不是：

```md
首轮回复 -> 工具 -> followup -> 结束
```

更可能是：

```md
首轮回复 -> 工具A -> followup -> 工具B -> followup -> 结束
```

因此状态机必须支持内部循环。

## 3.4 工具中间态应逐步从 committed history 中分离

第一阶段允许继续将 `tool_feedback` 写入历史，但必须先打上 `ephemeral` 标记。

长期目标是：

- committed history：保留用户消息、关键 assistant 回复、必要摘要
- ephemeral runtime：保留工具调用、工具结果、中间错误、临时上下文

## 3.5 UI 必须对“运行工具中”有明确反馈

不能在 `running_tools` 时只缓存不渲染而没有任何提示，否则用户会认为系统卡死。

第一阶段至少需要有：

- 正在分析工具调用...
- 正在执行 file\_operations...
- 正在生成后续回答...

***

# 四、建议的新回合状态

第一阶段建议使用以下状态：

```md
idle
streaming_initial_reply
detecting_tools
running_tools
generating_followup
finalized
```

说明：

- `idle`：空闲态
- `streaming_initial_reply`：首轮 assistant 文本流式输出中
- `detecting_tools`：正在检测本轮是否存在工具意图
- `running_tools`：正在执行工具
- `generating_followup`：工具执行后，正在生成 assistant followup
- `finalized`：本轮已经完成，允许正式消息接管 UI

第二阶段若进一步增强，可升级为带循环语义的状态结构，但第一阶段不必过早复杂化。

# 六、分阶段执行计划

## 阶段 1：打通回合状态主链

### 目标

建立从 APISource → ToolConversationLoop → Worker → ChatPage 的统一 `round_state` 状态传播链。

### 待办


### 推荐落点

#### `app/core/api_source.py`

新增字段建议：

```python
{
  "round_state": "idle",
  "selected_tool_protocol": None,
  "tool_candidates": [],
```

新增方法建议：

在以下时机写入状态：

```md

命中工具并开始执行 -> running_tools
工具执行后开始生成 followup -> generating_followup
整轮结束 -> finalized
```

#### `app/core/worker.py`

新增或复用一个 round state 信号：

```python

```

payload 示例：


### 完成判定

```md
[ ] API 工具执行过程中，UI 能收到明确 round_state
```

## 阶段 3：统一工具路由结果结构

### 目标

- `run_tool_round_from_messages()` 返回 `ToolRoundResult`
- `maybe_handle_tool_from_messages()` 兼容链仍可能返回拼接字符串

这会导致后续协议扩展时结构混乱。

### 待办

```md

[ ] 在 ToolRouterService 中增加候选选择逻辑
[ ] 让 Markdown `tool_call` fallback 也统一返回 ToolRoundResult
[ ] 让 legacy exec code block fallback 也统一返回 ToolRoundResult
```

### 推荐落点

#### `app/core/services/tool_router_service.py`

建议新增方法：

```python
def collect_tool_candidates(self, chat_id: str, messages: list) -> list
```

候选结构建议：

```md
native_fc > markdown_tool_call > legacy_exec_code
```

# 九、风险与注意事项

## 9.1 不要一次性重写太多层

当前应优先控制改动范围，避免：

- 同时重构 UI 状态机
- 同时重构工具执行器
- 同时重构 committed / ephemeral 存储
- 同时接入 native FC

这样会导致问题定位困难，回滚成本高。

## 9.2 不要把 `end_stream()` 当作“本轮最终完成”

`message_area_stream.py` 中的 `end_stream()` 最多只能代表：

```md
首轮 assistant 流式回复结束
```

不能代表：

```md
整轮 Agent 回合结束
```

## 9.3 不要继续扩大“字符串型 fallback 返回”

后续所有工具执行路径，都应尽量收敛为统一结构返回，而不是继续拼接日志字符串作为主数据结构。

## 9.4 不要在第一轮就强行做并发工具执行

虽然未来需要考虑并发工具，但第一轮建议保持：

```md
单轮只选一个最终协议
单次只执行一个主工具调用
```

先把状态机稳定下来，再扩并发。

# 十一、结论

本计划的核心不是“立刻让原生 FC 和 Markdown `tool_call` 共存”，而是：

**先把 API 模式中的单回合状态机理顺。**

只有当以下三件事成立后，双协议共存才不会进一步恶化系统复杂度：

1. UI 能正确理解“流式中 / 工具中 / followup 中 / finalized”
2. 工具路由能统一输出结构化结果
3. 中间态消息能够被标记并逐步从 committed history 中分离

因此，推荐的严格执行顺序是：

```md
先状态机
再统一工具路由
再标记 ephemeral
最后再接 native FC
```

这份计划书可作为后续 AI 或工程师实施改造时的统一执行依据。

# 一、文档目的

本清单不是讲“为什么改”，而是讲：

- **先改哪里**
- **后改哪里**
- **哪些地方先不要动**
- **每一步做完要怎么验证**

适合在正式实施前作为操作顺序指南使用。

***

# 二、总原则

## 2.1 顺序原则

严格遵守以下顺序：

```md
先打通 round_state 主链
再让 UI 基于 round_state 渲染
再统一工具路由结果结构
再补 ephemeral 标记
最后为 native FC 预留入口
```

## 2.2 风险控制原则

第一轮不要同时推进以下几件事：

```md
[√] 不要同时重构 committed / ephemeral 存储
[√] 不要同时把 followup 改成流式
[√ ] 不要同时引入并发工具执行
[√ ] 不要同时接入真正可执行的 native FC
```

## 2.3 验证原则

每完成一小阶段，都至少验证：

```md
[ ] 语法是否正常
[ ] API 聊天是否仍能发送
[ ] 首轮流式是否仍能显示
[ ] tool loop 是否仍能跑通
[ ] UI 是否没有明显倒退
```

# 四、阶段 A：先补 round\_state 主链（最优先）

## 目标

先让系统具备“知道当前回合在哪个阶段”的能力，但尽量不大改原有执行逻辑。

## 先改哪些文件

```md
1. app/core/api_source.py
2. app/core/tool_runtime/conversation_loop.py
3. app/core/worker.py
```

## 为什么先改这三个

因为这三个文件共同构成：

```md
回合状态源头 -> 工具后半段协调 -> 向 UI 转发
```

如果先改 UI 而不先打通这条状态链，UI 只能猜，最终还是补丁逻辑。

# 十、明确不要先动的区域

为了控制风险，以下区域建议在第一轮尽量不动或少动：

```md
[ ] Browser 模式主链
[ ] MainWindow 大量面板初始化逻辑
[ ] ContextManager 的底层消息存储结构
[ ] llm_provider.py 的流式协议细节
[ ] committed / ephemeral 的彻底拆分
[ ] followup 的流式化
[ ] 并发工具执行
```

原因很简单：

这些点一旦同时动，会让问题来源不清晰，排查成本急剧上升。

***

# 十一、推荐提交粒度

建议按阶段拆提交，而不是混成一大坨：

```md
提交 1：补 round_state 字段与信号链
提交 2：ChatPage 改为看 round_state
提交 3：ToolRouter 统一返回结构
提交 4：tool_feedback 增加 ephemeral 标记
提交 5：native FC 占位入口
```

这样出了问题更容易回滚和定位。

***

# 十二、结论

如果只记住一句话：

**先让系统知道“这一轮到底结束了没有”，再去谈双协议工具调用。**

本实施顺序清单的核心价值在于：

- 先补状态链，避免 UI 靠猜
- 先稳住现有流式 + tool loop 交接
- 再统一工具路由结构
- 最后再把 native FC 接进来

严格按此顺序推进，能最大程度降低“改到一半又回滚”的概率。

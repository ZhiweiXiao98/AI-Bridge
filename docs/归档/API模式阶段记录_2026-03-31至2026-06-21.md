## 1. 背景与目标

经过近阶段接入、修复与审计，API 模式已经明显超出“只能跑通”的早期阶段：配置中心、对话存储、上下文工作台、Prompt Assembly、工具运行时与工具闭环都已出现真实落地代码。但与此同时，文档、命名与实际实现之间已经出现多处偏差，容易让后续开发者与 AI 协作者误判现状。

当前阶段项目策略仍保持不变：
- Browser 模式：主生产模式（Primary Production Mode）
- API 模式：副模式 / 孵化模式 / 商业化预备模式（Secondary Incubation Mode）

因此，API 模式近期目标仍不是追求与 Browser 完全对称，也不是推动“API 主导式架构统一”，而是：

1. 继续巩固 API 配置中心与运行时配置真相
2. 把上下文系统从“可用引擎”继续推进为“可管理、可观测、可控制的产品能力”
3. 把工具运行时从“局部可用”推进到“主链清晰、策略明确、闭环稳定”
4. 在不影响 Browser 主链稳定性的前提下，逐步提升 API 模式可用性、调试性与商业化预备度

## 2. 当前现状盘点（以代码现实为准）

### 2.1 已有能力

当前 API 模式已经具备以下现实能力：
- `APISource`：负责 API 模式消息收发、对话管理、配置加载、上下文工作台读写
- `ConversationStore`：负责多对话持久化、切换、删除、重命名、置顶、无副作用快照读取与指定对话 ContextManager 构建/回写
- `ContextManager`：具备 system / long_term / working / short_term 四层骨架，以及 token 预算统计能力
- API 对话列表：支持新建、删除、原位重命名、置顶、排序
- API 基础消息收发：支持同步发送与流式发送
- API 多对话排序：已按 `last_message_at` 稳定排序，切换不会再导致列表乱跳
- 上下文工作台：已升级为 API 多对话控制台第一版，支持显式 `conversation_id` 目标读写
- Prompt Assembly：已存在独立运行时模块 `app/core/prompt_runtime/`
- Prompt 运行时拆分：已存在 `prompt_assembler.py`、`skills_prompt_loader.py`、`system_policy_loader.py`
- Skills Prompt：已通过 `SkillsManager.generate_system_prompt()` 真实进入 final system prompt
- System Policy：已通过 `docs/API模式系统策略.md` 真实进入 final system prompt
- final system prompt：会在发送前写入 `ContextManager`，并作为真实 system message 参与模型请求
- 工具运行时：已存在 `app/core/tool_runtime/`，其中 `models.py`、`segment_parser.py`、`executor.py` 已落地
- `ToolRouterService`：默认优先走 `tool_runtime` 新主链，仅在未命中时回退旧兼容链
- API 工具闭环：已实现“单轮工具执行 → 工具结果回灌 → 自动续答一轮”的最小闭环
- API 结构化消息模型：已落地 `ConversationMessage`、兼容转换器与 `tool_feedback` 类型，工具反馈不再只是扁平 history 文本
- Gemini Provider：已接入 `GeminiProvider`，并纳入统一 provider 工厂与 API 模式初始化主链
- SettingsPage 多 Provider 配置：已支持 `openai_compatible / gemini / mimo` 切换、模型候选联动、Provider 回显、`proxy_url` 保存、原生工具探测和可用模型探测
- MiMo Profile：已按官方 OpenAI-compatible Chat Completions 形态处理 `api-key`、`max_completion_tokens`、`thinking` 开关，并对 `/models` 返回的 ASR/TTS 模型做聊天模型过滤
- API 聊天栏：已支持当前会话级 Profile/Chain、模型、思考开关和强度选择；这些覆盖配置会参与发送、流式发送、模型探测和工具探测，reasoning 控件已由 `model_capabilities` V1 按模型能力动态显示；输入框已接入 Slash Skill 引用 V1，输入 `/` 展开 Skills 建议，`/skill_name ...` 会归一化为 Codex 风格的 `$skill_name ...` 对话引用
- API 上下文提示：聊天栏已用环形进度 + tooltip 展示上下文总量与 system / long-term / working / short-term / output reserve 明细
- 历史删除能力：对话删除功能已完成；消息索引删除能力已在 source/worker 层存在
- 工具消息折叠显示：API / Browser 两端的工具执行结果消息已完成统一折叠显示关键修复，并已稳定识别为可折叠工具消息

### 2.2 当前关键缺口

当前 API 模式仍存在以下核心待收口点：

#### A. 配置层
- 设置页中的 API 配置、运行时配置、工作台展示仍有进一步统一空间
- `provider profile / fallback chain / 自动降级` 已完成第一版闭环，且 Gemini 已完成基础接入；provider 错误分类 V1 已接入 retry / fallback 事件，后续重点转向更细供应商映射与体验精修
- “当前生效配置”已完成第一版明确展示，并已区分“配置主 Profile”与“当前运行 Profile”
- SettingsPage 已具备 Provider 切换、Gemini 模型候选联动、`proxy_url` 输入与保存，但代理是否对 Gemini 严格受控仍保留观察
- “深度思考”等 API 特性开关已完成设置页入口和聊天栏会话级入口；reasoning 控件已接入能力解析 V1，能区分不支持、仅开关和 `reasoning_effort` 三档形态，后续仍需把 tools / stream / fallback 等能力纳入同一能力表
- 历史字段命名 `inject_ai_readme` 已与现实语义脱节：当前其真实控制的是 System Policy 注入，而非 AI_README 注入

#### B. 上下文层
- `ContextManager` 已接入真实产品链路，但工作台来源树可视化仍未完全展开
- Context Workspace UI 已完成一轮 `panel / logic / presenter` 分层收口，但 Prompt 来源树、token 口径与参数控制面仍待继续产品化
- final system prompt 已可查看，但来源块尚未完整展示为 default / skills / policy / conversation 四层
- Long-term Memory 尚未形成稳定的策略化 RAG 管理能力
- Working Memory 已具备查看/编辑/清空与基本结构，但尚未升级为真正的 Agent 任务状态机
- Short-term Memory 的滑动窗口仍缺少正式用户级调参界面
- Output Reserve / Safety Margin 目前仍主要停留在配置层，而非强产品化控制层
- Browser 模式的对等上下文工作台仍未接入

#### C. 工具能力层
- `tool_runtime` 核心三件套已落地，但 `markdown_parser.py` / `conversation_loop.py` / `policies.py` 尚未独立落地
- `ToolRouterService` 已形成“新主链 + 旧兼容链”的混合结构，但尚未完全瘦身为薄桥
- 新链当前主要覆盖标准化 code segments；对复杂 Markdown 污染、纯 text 回退、旧格式兼容仍部分依赖旧链
- API 模式下的工具闭环已存在，但仍是嵌在 `worker.py` 中的最小单轮闭环，而非独立 conversation loop 模块
- 工具 availability / visibility / execute 权限的统一解析层尚未形成

#### D. 体验层
- 流式打字效果、加载态、任务框架显示仍可继续增强
- Prompt 来源树可视化尚未完全展开
- 聊天栏上下文容量提示已完成最小可视化，但预算控制面仍需和 Context Workspace / 设置页统一
- 工具结果展示虽然已完成统一折叠关键修复，但摘要提炼能力、结构化块表达仍可继续提升
- Browser 与 API 在工具闭环体验与运行时控制层面尚未完全统一

## 3. 当前阶段开发原则

### 原则 A：不伤 Browser 主链
凡是可能影响 Browser 主生产链稳定性的全局改造，当前阶段一律降级优先级。

### 原则 B：共享能力，不强求共享全部状态机
短期内建议继续共享：
- ToolRouter
- DockerManager
- FileService
- Skills 能力
- 代码渲染组件
- Prompt Runtime / Tool Runtime 的可复用中间层

短期内不强求共享：
- 会话状态机
- 页面生命周期
- 当前视图 ID 管理
- Browser 与 API 的全部闭环控制流程

### 原则 C：先把 API 模式做成“可控运行时”，再继续打磨“优雅产品”
当前阶段优先推进：
- 配置真相可观测
- Prompt 真相可观测
- 上下文可控制
- 工具可验证
- 闭环可解释

### 原则 D：以代码现实为准，同步纠正文档与命名认知
后续推进中，任何计划判断都应尽量先以代码审计验证，而不是依赖旧对话记忆或历史文档印象。

## 6. Phase C：工具运行时与无状态工具闭环（P1）

### 6.1 当前判断
Phase C 已不再是纯规划阶段。`tool_runtime` 核心骨架已落地，`ToolRouterService` 默认优先走 runtime 新主链；同时 API 模式下已实现最小单轮工具闭环，且结构化消息模型与 `tool_feedback` 已进入主链。当前重点从“是否接入”转向“如何继续收口”；连续多轮 conversation loop 仍未完成。

### 6.2 已完成内容

#### A. `tool_runtime` 核心三件套已落地
当前已存在：
- `app/core/tool_runtime/models.py`
- `app/core/tool_runtime/segment_parser.py`
- `app/core/tool_runtime/executor.py`

其中：
- `models.py` 已定义 `ToolIntent` / `ToolExecutionResult` / `ToolRoundResult`
- `segment_parser.py` 已支持从标准 code segments 提取：
  - `tool_call` → `skill_call`
  - `python/py + # EXEC/#RUN/#EXECUTE` → `exec_code`
- `executor.py` 已统一执行：
  - `skill_call` → `SkillsManager.execute_skill()`
  - `exec_code` → `DockerManager.execute_code()`

#### B. `ToolRouterService` 已形成“新主链 + 旧兼容层”结构
当前 `ToolRouterService` 默认优先执行：
- `ToolSegmentParser.parse_messages(...)`
- `ToolRuntimeExecutor.execute_intents(...)`

仅当新链未命中时，才回退到旧兼容逻辑：
- `_extract_raw_text()`
- `_handle_function_calling()`
- `_handle_code_blocks()`

这意味着：
- runtime 新主链已建立
- 旧 Markdown / 正则提取链已退居 fallback 兼容层

#### C. API 模式已实现最小单轮工具闭环（Phase C-2 第一版）
在 `worker.py` 的 API 发送主链中，当前已经实现：
1. 用户消息发送
2. AI 回复生成
3. 对最新 AI 回复进行工具解析与执行
4. 将工具结果以 `tool_feedback` / `🔧 [工具执行结果]` 形式回灌历史
5. 自动调用 `continue_assistant_reply_sync()` 再续答一轮

因此，当前 API 模式已经具备：
- 单轮工具执行
- 结构化工具结果回灌
- 自动续答一轮

但截至 2026-04-08，连续多轮自动工具循环仍未稳定实现；当前更符合“单轮闭环 + 一次续答”的阶段状态。

### 6.3 待继续深化

#### A. 协议层补齐
- `markdown_parser.py` 尚未独立落地
- 纯 text 回退提取、复杂 Markdown 提纯、旧格式兼容仍部分依赖旧链
- 新链覆盖面仍可继续扩大，以进一步压缩旧链使用面

#### B. 闭环层收口
- 当前最小工具闭环仍内嵌在 `worker.py` 中
- 尚未抽离为独立 `conversation_loop.py`
- 尚未支持多轮 loop、最大自动轮数、防无限循环策略
- 尚未形成统一策略层控制工具执行 / 自动续答边界

#### C. 策略层与可用性解析
- `policies.py` 尚未独立落地
- 工具 availability / visibility / execute 权限的统一解析层尚未形成
- Prompt 暴露、可执行集合、UI 启用状态仍缺少统一快照源

#### D. 结构化回灌
- 当前工具结果已不再只是扁平 assistant 文本，`tool_feedback` 与结构化消息模型已进入 API 主链
- 但对外请求侧与自动循环侧仍未演进到更标准化的 tool role / 原生 tools/function calling 结构

### 6.4 当前优先验证对象
- `file_operations`
- `code_execution`
- `knowledge_search`
- `web_search`
- 代码审查相关无状态链路

### 6.5 当前更准确的阶段结论
Phase C 当前不应再表述为“准备接入工具”，而应表述为：

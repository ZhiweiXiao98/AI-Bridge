# API 流式聊天状态架构 RFC（产品级）

- 文档状态：Draft
- 目标读者：客户端/服务端开发、QA、产品
- 适用范围：`app/ui/pages/chat/*`、`app/core/api/*`、`app/core/worker_modules/*`、`app/core/remote_worker.py`

---

## 1. 背景与问题陈述

当前链路已证明：

1. 服务端流式事件（`api_stream_chunk/status`）持续发送；
2. 客户端 `RemoteWorker -> ChatPageStreamManager -> ChatPage._on_api_stream_event` 可持续接收；
3. 状态层 `ApiChatStateStore` 中 `accumulated` 随 chunk 递增。

但用户体验层面仍存在：

- 流式可视化不稳定（体感“长时间无变化”）；
- 渲染行为难预测、难定位；
- 页面逻辑与渲染细节耦合严重，不利于维护与扩展。

核心原因不是单点 bug，而是**架构缺少“状态-投影-渲染”契约分层**。

---

## 2. 目标

### 2.1 可维护
- 单一状态真相（Single Source of Truth）
- 明确的职责边界：State / Projection / Render
- 消除“页面直接拼装渲染细节”的隐式逻辑

### 2.2 可扩展
- 支持更多流式形态（文本、工具调用、思考轨迹）
- 支持会话切换、并发会话、历史回放
- 支持将来分页/虚拟列表替换

### 2.3 可验证
- 事件顺序可检验（seq）
- 状态转移可单测
- 渲染延迟、丢帧、首帧时间可观测

---

## 3. 非目标

- 本 RFC 不要求一次性重写全部 UI；
- 不要求立即替换所有历史消息渲染路径；
- 不改变已有业务语义（User/AI 消息结构）下逐步迁移。

---

## 4. 架构总览

```text
Transport Events
  -> Domain State Store
  -> Projector (ViewModel)
  -> Render Patch Queue
  -> MessageArea Renderer
```

### 4.1 Domain State（领域状态层）
- 建议沿用并增强 `ApiChatStateStore`
- 仅负责状态转移，不关心 UI 可见窗口/滚动策略

### 4.2 Projector（投影层）
- 新增 `ApiChatProjector`
- 输入：state + viewport policy
- 输出：`ViewModel` + `Patch`

### 4.3 Renderer（渲染层）
- `MessageArea` 从“全量 render”转为“patch apply”
- 支持 append/update/remove/replace_range

---

## 5. 统一事件协议（前后端契约）

建议所有流式事件统一字段：

- `conversation_id: str`
- `round_id: str`
- `stream_id: str`
- `seq: int`（单调递增，按 stream 维度）
- `kind: started | delta | completed | cancelled | error`
- `delta: str`（仅 delta 时）
- `accumulated: str`（可选，但推荐）
- `ts_ms: int`

约束：
- 同一 `stream_id` 的 `seq` 必须严格递增；
- `completed/cancelled/error` 之后不得再发 `delta`；
- `round_id` 不可为空（否则事件丢弃并计数）。

---

## 6. 状态机定义

### 6.1 User 侧
- `PendingUser(client_msg_id, round_id)`
- `CommittedUser`

转移：
- 发送 -> PendingUser
- 历史同步命中（cid 或 round_id）-> CommittedUser（移除 pending）

### 6.2 AI 流式侧
- `StreamStarted`
- `Streaming(accumulated)`
- `StreamCompleted` / `Cancelled` / `Error`

转移：
- started -> streaming* -> completed
- completed 后等待 committed AI 对账，超时告警

---

## 7. 投影规则（Projector）

输出顺序规则：
1. committed 历史（原序）
2. pending user（未对账）
3. streaming ai（按 round 插入：对应 user 后，否则末尾）

冲突规则：
- 若 committed 中已存在同 round 的 AI，删除 streaming 临时项；
- 若 committed 中存在同 round 的 User，删除 pending user。

Patch 生成规则：
- started: append placeholder（可选）
- delta: update 同一 stream bubble 内容
- completed: remove ephemeral（若 committed AI 已到）或标记完成态

---

## 8. 渲染层契约

`MessageArea` 新接口建议：

- `apply_patch(patch: RenderPatch)`
- `set_tail_policy(policy: TailPolicy)`
- `snapshot_metrics() -> dict`

`RenderPatch`：
- `append(items)`
- `update(item_id, fields)`
- `remove(item_id)`
- `replace_range(start, end, items)`

禁止：
- 流式路径中每个 chunk 走全量 `render_messages(list)`。

---

## 9. 可观测性（Observability）

新增指标：
- `stream_first_paint_ms`
- `delta_to_paint_ms_p50/p95`
- `render_patch_queue_depth`
- `render_patch_drop_count`
- `stream_orphan_count`（有 started 无 completed）
- `reconcile_mismatch_count`

新增日志规范：
- 每条流仅打印关键里程碑（started/first_delta/completed）
- 高频 delta 使用采样日志（如每 20 条）

---

## 10. 测试策略

### 10.1 单元测试
- Store 状态转移
- Projector 插入位置、去重、对账
- seq 乱序与重复事件处理

### 10.2 集成测试
- 高频 chunk 压测（>100 chunks/s）
- 模式切换中流式不中断
- 新建会话/切会话下 round 不串线

### 10.3 回归测试
- `User -> StreamingAI -> CommittedAI`
- 无重复 User
- 流结束后内容一致

---

## 11. 迁移计划（分阶段）

### Phase 1（兼容引入）
- 引入 `ApiChatProjector`（只读并行）
- 保留现有渲染，增加 patch 结果对比日志
- 不改 UI 行为

### Phase 2（双写验证）
- 页面层同时产出全量渲染与 patch 渲染（灰度开关）
- 指标对比：一致性、延迟、抖动

### Phase 3（切主路径）
- 流式路径切到 patch 渲染
- 保留全量渲染作为 fallback（开关）

### Phase 4（清理收口）
- 删除流式路径中的全量 render 逻辑
- 统一事件契约与日志规范

---

## 12. 风险与回滚

风险：
- Patch 渲染引入新类型一致性 bug
- 旧组件（ChatBubble）字段依赖不完整

回滚：
- Feature Flag：`chat.api_stream_patch_render_enabled`
- 一键退回全量渲染路径

## 14. 验收标准（Definition of Done）

1. 功能：
- 稳定呈现 `User -> StreamingAI -> CommittedAI`
- 无重复 User

2. 性能：
- `stream_first_paint_ms < 300ms`（本地网络）
- `delta_to_paint_ms_p95 < 120ms`

3. 质量：
- 关键状态机单测覆盖 >= 90%
- 集成回归用例全部通过

4. 可运维：
- 指标可见、日志可追踪、可开关回滚。

# ai-ide 上下文压缩改造计划 v1

## 1. 文档目标

本文档基于 ai-ide 当前代码现实，提出一套可渐进落地的上下文压缩与消息结构升级方案。

本次计划不追求一步到位做成完整的“高级长上下文系统”，而是优先建设一条可持续演进的主线：

1. 先统一结构化对话消息模型
2. 再在结构化消息之上实现历史消息摘要压缩
3. 再继续扩展工具结果降噪、压缩状态、工作台与可视化能力
4. 尽量让本次建设可以同时反哺 API 模式与 Browser 模式

本文档重点解决的问题包括：
- 当前 short-term history 只有删除策略，没有压缩策略
- 当前工具结果虽然已形成闭环，但进入 history 后仍以大段文本为主，容易迅速占满上下文
- 当前 history 模型过于扁平，缺少消息分类与结构表达能力
- 当前上下文工作台与可视化已存在，但尚未形成统一的消息结构与压缩状态表达
- Browser 模式仍是开发主力，因此本次设计应尽量沉淀为可被 Browser/API 共享的能力，而不是只做 API 模式补丁

## 2. 当前代码现实与架构基线

### 2.1 当前 API 模式上下文主链

当前 API 模式的真实主链如下：

1. `APISource` 在发送前调用 Prompt Runtime，组装 final system prompt
2. final system prompt 写入 `ContextManager`
3. 用户消息通过 `ContextManager.add_message()` 进入 history
4. `ContextManager.build_messages()` 组装 system / long-term / working / history
5. `LLMProvider` 发起模型请求
6. assistant 回复再次通过 `ContextManager.add_message()` 回写 history
7. `ConversationStore.save_current()` 将上下文状态持久化到单对话 JSON 文件

因此，任何压缩与消息结构升级方案都应优先沿这条主链增强，而不是旁路重做一套新系统。

### 2.2 当前四层上下文模型

`ContextManager` 当前已具备以下分层：
- System Layer：`_system_content`
- Long-term Memory：`_long_term_fragments`
- Working Memory：`_working_memory`
- Short-term Memory：`_history`

并已具备：
- token 计数能力
- 各层 budget 概念
- output reserve
- short-term 的轮数/预算裁剪
- `get_token_usage()` 观测接口

当前问题不在于“没有上下文系统”，而在于：
- short-term 仍是删除型治理
- history 仍是扁平文本消息
- 缺少压缩与结构分层

### 2.3 当前持久化基础

`ConversationStore` 当前每个对话文件已保存：
- `conversation_system_prompt`
- `system_prompt`
- `history`
- `long_term`
- `working`
- `token_usage`
- `meta`

这意味着后续新增：
- 结构化消息字段
- compact state
- compact summary
- 保留区信息
- Browser/API 运行时状态快照

都可以自然挂载在现有单对话 JSON 中，而无需另起复杂存储系统。

### 2.4 当前工具闭环基础

当前 API 模式工具运行时已真实落地：
- `tool_runtime/models.py`：定义 `ToolIntent` / `ToolExecutionResult` / `ToolRoundResult`
- `tool_runtime/segment_parser.py`：从 code segments 提取工具调用意图
- `tool_runtime/executor.py`：统一执行 skill call / exec code
- `worker.py`：已实现“单轮工具执行 → 工具结果回灌 → 自动续答一轮”的最小闭环

这说明：
- 当前系统已经拥有内部结构化工具语义
- 但这套结构尚未完整提升到 history 表达层
- 工具结果进入上下文时仍然偏文本化

### 2.5 当前上下文可观测与控制面

当前 UI 已有：
- `ContextWorkspacePanel`：多对话上下文控制台
- `ContextVisualPanel`：五层 token 占用可视化

这意味着后续可以在同一控制面中继续纳入：
- 结构化消息状态
- compact state
- compact summary 预览
- Browser/API 运行时上下文真相
- 阈值与策略控制

## 3. Browser / API 双模式共享目标

### 3.1 本计划的共享设计原则

虽然当前 API 模式更容易先落地上下文主链增强，但 Browser 模式仍然是当前开发主力。因此，本计划不应把消息结构与压缩设计做成“API 专用补丁”，而应尽量沉淀为 Browser / API 可共享的中间层能力。

本次计划建议坚持以下原则：

1. **优先建设共享消息结构层**
   - 会话消息的结构定义应尽量独立于传输通道
   - API / Browser 最终都应能产出统一消息结构

2. **上下文压缩优先依赖内部结构，而不是界面文本表象**
   - 不论消息来自 API 还是 Browser，只要能标准化，就应复用同一压缩思路

3. **Browser 模式未来应接入真实网页运行时上下文能力**
   - 不只读消息内容，也要接入网页侧配置与上下文状态

### 3.2 Browser 模式未来可接入的关键能力

Browser 模式后续建议纳入以下能力：

- 从网页提取会话结构
- 读取网页侧 tokens / model / sampling params / system prompt
- 修改网页侧 model / sampling params / system prompt
- 将网页消息标准化为统一结构
- 把网页原生上下文能力纳入工作台 / 状态面板

### 3.3 Browser 模式当前可作为未来接入源的网页能力

根据当前已知信息，目标 AI 网页侧已经支持或展示以下能力：
- 输入系统提示词（角色预设）
- 调整上下文携带条目数
- 显示当前对话消耗 tokens 数
- 显示单次最大 tokens 数
- 调整随机性
- 调整话题新鲜度
- 调整重复度
- 选择模型
- 显示名称
- 删除某轮 / 某条对话
- 重新生成某轮 / 某条对话
- 引用某轮 / 某条对话
- 复制某轮 / 某条对话

虽然这些能力当前尚未接入 ai-ide 的统一上下文系统，但后续完全可以作为 Browser 模式上下文治理的第一手数据源与操作入口。

## 4. 当前核心问题诊断

### 4.1 Short-term Memory 当前只有“删除”，没有“压缩”

当前 `ContextManager._trim_history()` 的策略本质是：
- 超过最大轮数：删除最早消息
- 超过 short-term budget：删除最早消息

问题在于：
- 历史一旦超限会被直接丢弃
- 没有中间缓冲层
- 无法保留早期任务语义、关键决策与错误上下文
- 长任务连续性较弱

### 4.2 工具结果已进入主链，但对上下文不友好

虽然工具运行时已形成闭环，但当前工具结果进入 history 后仍以大段文本为主。这样会导致：
- Read / Grep / Search / 执行输出很容易撑满 short-term budget
- 工具结果与普通 assistant 文本混在一起，难以治理
- 当前裁剪策略无法优先处理低价值高 token 的工具噪音

### 4.3 History 模型过于扁平

当前 `ContextManager.Message` 仅包含：
- `role`
- `content`
- `token_count`
- `timestamp`

这意味着当前 history 不能稳定表达：
- 普通文本消息
- 工具反馈消息
- 摘要消息
- 元消息
- 压缩边界
- 原文与摘要并存关系

### 4.4 缺少压缩决策层

当前 API 主链基本是：
- build messages
- 直接请求模型

中间尚无正式的：
- token 压力判断
- 自动压缩触发器
- 压缩失败保护
- 摘要注入策略
- recent raw messages 保留策略
- compact state

这意味着当前上下文系统虽有分层，但还没有形成真正的 compaction runtime。

## 5. 本次改造的总目标

本次改造计划的总目标不是一次性实现完整多层压缩系统，而是在 ai-ide 当前架构上引入一条可渐进扩展的“结构化消息 + 历史压缩 + 双模式反哺”主线。

总目标拆分为四点：

### 5.1 建立统一的结构化对话消息模型
优先解决“消息是什么”的问题，为 API / Browser 两种来源提供共同的表达层。

### 5.2 建立基于结构化消息的 short-term 压缩能力
让系统在接近预算上限时，不再只删除旧消息，而能把较早历史压缩成摘要，并保留最近原文消息。

### 5.3 建立工具结果降噪能力
让工具结果在回灌与持久化时具备“摘要优先、原文可留存、上下文低噪”的能力。

### 5.4 建立可观测的 compact state 与上下文控制能力
让系统与工作台能够表达：
- 是否已经 compact
- compact 发生时间
- compact 原因
- 当前摘要区 / 最近原文区状态
- Browser/API 当前运行时上下文状态

## 6. 方案总览：三阶段演进路线

### 6.1 V1：统一结构化消息模型（最小可行版）

目标：先解决“对话消息如何统一表达”的问题，为 API 模式先落地，也为 Browser 模式未来接入留统一出口。

特点：
- 是上游基础设施建设
- 会直接影响 history 持久化、工具反馈表达、工作台数据表达
- 能为后续历史压缩提供更稳定输入

### 6.2 V2：基于结构化消息的 short-term 摘要压缩

目标：在结构化消息模型之上，实现旧历史摘要化 + 最近消息原文保留。

特点：
- 压缩器面对的是可分类消息而不是纯字符串
- 更容易区分工具反馈、普通消息、摘要消息、元消息
- 更适合后续继续演进

### 6.3 V3：工具降噪 / compact state / 双模式工作台增强

目标：在 V1 / V2 落地后，继续增强工具结果治理、压缩状态可视化、Browser/API 共用控制面与更丰富的上下文策略。

特点：
- 更接近成熟长会话系统
- 能更好反哺 Browser 模式
- 更适合在已有稳定结构上持续演进

## 7. V1 详细方案：统一结构化消息模型

### 7.1 为什么 V1 先做消息结构化

结构化消息属于上游事实建模，它会直接影响：
- history 如何持久化
- 哪些消息进入模型上下文
- 哪些消息只用于 UI 展示
- 哪些消息可 compact
- 哪些消息可折叠
- 哪些消息需要保留原始内容

如果这层不先统一，后续历史摘要逻辑就只能对扁平字符串做推断，容易在第二轮改造时推倒重来。

### 7.2 V1 的核心目标

V1 建议优先完成以下目标：

1. 定义统一的 Conversation Message Model
2. 让 API 模式历史消息逐步切换到该模型
3. 给工具反馈消息留出正式类型
4. 给 future compact summary 留出正式类型
5. 为 Browser 模式标准化网页消息预留相同出口

### 7.3 建议的结构化消息字段

建议结构至少包含：
- `role`
- `kind`
- `content`
- `raw_content`
- `timestamp`
- `token_count`
- `meta`
- `source_mode`
- `conversation_id`
- `visible_in_context`
- `compactible`

建议语义如下：

- `role`：消息角色，如 user / assistant / system
- `kind`：消息类型，如 text / tool_feedback / compact_summary / meta
- `content`：进入模型上下文的主内容，通常是精简后的文本
- `raw_content`：原始长文本，供 UI 展开、追溯或后续调试使用
- `timestamp`：消息时间
- `token_count`：消息 token 计数
- `meta`：附加结构信息，如 tool name、success、source tag、压缩边界等
- `source_mode`：来源模式，如 api / browser
- `conversation_id`：所属对话 ID
- `visible_in_context`：是否默认进入模型上下文
- `compactible`：是否允许被压缩器处理

### 7.4 建议的 kind 最小集合

V1 不建议一开始设计过多类型，建议最小集合为：
- `text`
- `tool_feedback`
- `compact_summary`
- `meta`

这样既足够支撑后续压缩，又不会在第一版引入过高复杂度。

### 7.5 结构化消息的两层语义

建议从设计上区分：

#### A. 会话消息层
用于持久化、UI、工作台、压缩器输入。

#### B. 上下文装配层
用于最终 `build_messages()` 时决定哪些消息真正进入模型上下文。

这样做的好处是：
- 有些消息可以进 history 但不进模型
- 有些消息可以保留原始信息但只让摘要参与推理
- Browser/API 的不同来源可以统一汇聚后再做装配

### 7.6 V1 与工具运行时的衔接

当前 Tool Runtime 已有：
- `ToolExecutionResult.display_text`
- `ToolExecutionResult.output`
- `ToolExecutionResult.error`

V1 建议通过适配层将其转换为统一消息结构：
- `display_text` → `content`
- `output/error` → `raw_content`
- `success/name/kind` → `meta`
- `kind='tool_feedback'`
- `source_mode='api'`

这意味着：
- 工具运行时模型可以复用
- history 层会获得正式工具反馈结构
- 未来 Browser 模式也可以用同样思路处理网页消息与操作结果

## 8. V2 详细方案：基于结构化消息的 short-term 摘要压缩

### 8.1 V2 的定位

V2 的目标是在 V1 结构化消息模型之上，正式建立历史压缩能力。

此时压缩器面对的输入不再是单纯字符串，而是带有：
- role
- kind
- content
- raw_content
- meta
- visible_in_context
- compactible

的统一消息结构。

这样压缩逻辑会更稳定，也更有扩展空间。

### 8.2 V2 核心机制

当请求前发现 short-term token 压力达到阈值时：

1. 选取较早结构化消息作为待压缩区
2. 保留最近若干条结构化消息作为保留区
3. 跳过不应被压缩的 meta 或特殊消息
4. 基于可分类消息生成 compact summary
5. 将待压缩区替换为一条 `compact_summary` 消息
6. 保留 recent raw messages 原文
7. 将 compact state 写回 `ConversationStore`

### 8.3 V2 摘要结构建议


> 实施备注（当前阶段约束时间2026-4-4）：
> - 当前已落地的 compact summary 允许先采用 **rule-based conservative summary** 作为过渡实现。
> - 该实现的目标是：稳定替换旧历史、为上下文续接提供保守桥接、为工作台展示提供可读摘要块。
> - 当前阶段**不应误认为**已经具备完整高级压缩能力；在尚未具备以下能力前，不追求过强的摘要智能化：
>   - fork agent
>   - 专门 compact prompt
>   - analysis + summary 两阶段
>   - 更完整的消息块语义
>   - 更强的 tool / API round / transcript / attachment 处理
> - 后续在上述能力具备后，再将当前保守结构化摘要升级为更强的 compact summary 体系。

建议采用适合 ai-ide 的 6 段式摘要：

1. 用户目标
2. 已完成工作
3. 关键文件与代码位置
4. 重要工具结果与结论
5. 当前问题 / 风险 / 失败原因
6. 下一步应继续的工作


当前代码状态补充说明：
- 当前实现的 compact summary 输出结构已经收敛为上述 6 段式模板。
- 但当前各章节内容仍主要基于 rule-based snippet / keyword 提取，属于 conservative summary，而非高智能语义压缩。
- 因此，“结构已对齐、能力仍保守”是当前 V2 摘要实现的真实状态。
相比直接对扁平历史做摘要，结构化消息能让该过程更容易抽取：
- 普通 text 中的任务推进
- tool_feedback 中的结论性信息
- meta 中的特殊边界信息

### 8.4 V2 保留区策略

建议不要简单保留“最近 N 条消息”，而是采用保守规则：
- 至少保留最近 2~4 轮 user/assistant 对
- 最近一次用户请求与最近一次 assistant 回复不可拆开
- 若最近包含工具反馈与自动续答，则尽量完整保留该轮闭环
- 若保留区过小不足以维持任务接续，则按 token 向前补足

### 8.5 V2 触发阈值建议

建议在现有 budget 基础上增加 auto compact threshold 概念：

- `effective_window = max_window_tokens - output_reserve`
- `auto_compact_threshold = effective_window - compact_buffer`

其中：
- `compact_buffer` 用户建议可调
- 默认值建议为 **24000**

该值在初版中可作为配置项写入上下文配置体系，但先采用保守默认值即可。

### 8.6 V2 触发时机建议

建议优先在 API 请求前触发，而不是等待请求失败后再补救。挂接点建议为：
- `APISource.send_message_sync()` 中 `build_messages()` 之前
- `APISource.send_message_stream()` 中 `build_messages()` 之前
- `continue_assistant_reply_sync()` 中 `build_messages()` 之前

未来 Browser 模式如果引入本地上下文工作台与浏览器侧会话标准化，也可以复用同类逻辑。

### 8.7 V2 失败保护建议

即使 V2 还属于第一批压缩落地，也建议加入最小失败保护：
- 压缩失败时不阻断主链
- 可回退到现有滑动窗口逻辑
- 连续失败次数写入 compact state
- 达到阈值后本轮跳过自动 compact，避免循环失败

## 9. V3 详细方案：工具降噪 / compact state / 双模式工作台增强

### 9.1 工具结果降噪增强

在已有结构化消息基础上，继续引入工具结果治理：
- tool_feedback 优先保留结论性摘要
- raw_content 可留存但不默认进入上下文
- 较早工具消息允许进一步微压缩
- 优先治理 read/search/exec 一类高 token 噪音消息

### 9.2 compact state 正式产品化

工作台与持久化层应能表达：
- compact 次数
- 上次 compact 时间
- 上次 compact 原因
- 最近摘要预览
- 保留区消息数量
- 是否处于 compact 失败保护状态

### 9.3 Browser/API 双模式工作台增强

后续建议把工作台从“当前主要面向 API 对话”推进到“统一上下文控制面”，逐步纳入：
- Browser 会话结构
- Browser 页面侧 model / tokens / sampling params / system prompt
- Browser 页面侧上下文携带条目数
- Browser 侧删除 / 重生成 / 引用 / 复制等能力的状态表达

### 9.4 更丰富的可视化

后续可继续增强：
- compact summary 占用
- recent raw 占用
- tool_feedback 占用
- Browser/API 当前运行时参数展示
- compact 状态标记

## 10. 建议新增/修改的数据结构

### 10.1 ConversationStore 建议新增 compact_state

建议在单对话 JSON 中新增：
- `compact_state.compact_count`
- `compact_state.last_compacted_at`
- `compact_state.last_trigger`
- `compact_state.consecutive_failures`
- `compact_state.last_summary_preview`
- `compact_state.recent_preserved_count`

## 13. 风险与兼容策略

### 13.1 风险：结构化消息改造影响旧数据
应对：
- 读取时兼容旧格式
- 未带 `kind` 的历史默认视为 `text`
- 不要求一次性迁移所有旧对话文件

### 13.2 风险：过早做复杂类型体系导致开发负担过高
应对：
- V1 只保留最小 kind 集合
- 先建立骨架，不在第一版引入过多消息类型

### 13.3 风险：工具结果降噪后丢失重要细节
应对：
- `content` 保留摘要
- `raw_content` 保留原文
- working memory 保留结论
- UI 保留展开入口

### 13.4 风险：摘要质量不稳定
应对：
- 先在结构化消息基础上做摘要
- 使用稳定、简洁的固定模板
- 失败时允许回退到现有滑动窗口逻辑

### 13.5 风险：Browser 与 API 路线再次割裂
应对：
- 先统一消息结构层
- Browser/API 各自不同的采集与执行链路，尽量复用同一消息表达与状态协议

## 14. 本计划的阶段性结论

基于 ai-ide 当前代码现实，本轮最合理的演进路线应调整为：

1. 先统一结构化消息模型
2. 再做基于结构化消息的历史摘要压缩
3. 再继续推进工具降噪、compact state 与工作台增强
4. 让 API 模式先落地，同时为 Browser 模式接入做好结构准备

这条路线相比“先做压缩、后补结构”更稳健，因为：
- 结构是上游事实建模
- 压缩逻辑依赖结构质量
- 结构层更容易沉淀为 Browser/API 共享能力
- 更符合当前 Browser 模式仍是开发主力的现实

## 16. 统一 Conversation Message Model 样例

本节用于把“结构化消息模型”从抽象字段说明，收敛到可执行的统一样例，避免后续不同实现者对字段语义产生分歧。

### 16.1 dataclass 设计草案（示意）

以下为建议的数据结构草案，用于指导后续代码实现；本节是协议草案，不要求当前代码立即与该示意一字不差完全一致。

```python
@dataclass
class ConversationMessage:
    role: str                     # user / assistant / system
    kind: str = 'text'            # text / tool_feedback / compact_summary / meta
    content: str = ''             # 进入模型上下文的主内容
    raw_content: str = ''         # 原始完整内容，可供 UI / 调试 / 展开查看
    timestamp: float = 0.0
    token_count: int = 0
    meta: Dict[str, Any] = field(default_factory=dict)
    source_mode: str = 'api'      # api / browser
    conversation_id: str = ''
    visible_in_context: bool = True
    compactible: bool = True
```

### 16.2 字段约束建议

- `role`
  - 允许值：`user` / `assistant` / `system`
  - 与现有主链兼容，不建议第一版扩出更多 role

- `kind`
  - 第一版最小集合：`text` / `tool_feedback` / `compact_summary` / `meta`
  - 后续如需细分再扩展，不建议第一版预埋过多类型

- `content`
  - 面向模型与普通历史查看的“主内容”
  - 应尽量短于 `raw_content`

- `raw_content`
  - 原始长文本
  - 可为空
  - 用于 UI 展开、调试回看、工具长输出保存

- `meta`
  - 用于承载结构化附加信息
  - 第一版应允许为空字典
  - 不建议在第一版把主语义塞进 `meta` 而让顶层字段失真

- `visible_in_context`
  - 决定 `build_messages()` 时是否默认参与模型上下文
  - 建议第一版显式使用，避免后续大量隐式规则散落在调用层

- `compactible`
  - 决定该消息是否允许被压缩器处理
  - 该字段不代表一定会被压缩，只表示“具备被处理资格”

## 17. compact_state JSON 结构样例

### 17.1 推荐结构

```json
{
  "compact_state": {
    "compact_count": 0,
    "last_compacted_at": 0,
    "last_trigger": "",
    "consecutive_failures": 0,
    "last_summary_preview": "",
    "recent_preserved_count": 0,
    "disabled_until_manual_retry": false
  }
}
```

### 17.2 字段语义

- `compact_count`
  - 已执行成功的压缩次数
  - 默认值：`0`

- `last_compacted_at`
  - 最近一次成功压缩时间戳
  - 默认值：`0`

- `last_trigger`
  - 最近一次触发原因，如：`auto_threshold` / `manual` / `pre_request`
  - 默认值：空字符串

- `consecutive_failures`
  - 连续压缩失败次数
  - 默认值：`0`

- `last_summary_preview`
  - 最近一次摘要预览文本，供工作台快速显示
  - 默认值：空字符串

- `recent_preserved_count`
  - 最近一次压缩中保留的原文消息数量
  - 默认值：`0`

- `disabled_until_manual_retry`
  - 若压缩器持续失败，可进入临时禁用状态，等待手动恢复
  - 默认值：`false`

### 17.3 老会话兼容策略

若旧对话 JSON 中不存在 `compact_state`：
- 读取时自动补默认值
- 写回时再正式落盘
- 不要求一次性迁移旧文件

### 17.4 字段分类建议

#### 参与逻辑判断的字段
- `compact_count`
- `last_compacted_at`
- `last_trigger`
- `consecutive_failures`
- `recent_preserved_count`
- `disabled_until_manual_retry`

#### 主要用于 UI 展示的字段
- `last_summary_preview`

## 18. 上下文装配规则表

本节明确“会话消息层”与“上下文装配层”的衔接规则，避免后续逻辑散落在 `build_messages()`、Worker、UI 或压缩器中各自猜测。

### 18.1 默认装配规则

| kind | 持久化到 history | 默认进入模型上下文 | 默认可被压缩 | 典型用途 |
|------|------------------|--------------------|--------------|----------|
| `text` | 是 | 是 | 是 | 普通 user / assistant 对话 |
| `tool_feedback` | 是 | 是 | 是 | 工具结果摘要化反馈 |
| `compact_summary` | 是 | 是 | 否 | 历史压缩后的摘要承载 |
| `meta` | 是 | 否 | 否 | 边界、说明、调试、标记 |

### 18.2 build_messages() 建议规则

建议 `build_messages()` 在处理 history 时遵循以下原则：

1. 只装配 `visible_in_context == true` 的消息
2. 默认跳过 `kind == meta` 的消息
3. 对 `tool_feedback` 使用 `content` 进入模型，不使用 `raw_content`
4. 对 `compact_summary` 直接使用 `content`
5. `raw_content` 仅用于 UI / 调试 / 展开查看，不直接进入模型上下文

### 18.3 压缩器建议规则

压缩器处理 history 时，建议遵循：

1. 仅处理 `compactible == true` 的消息
2. 默认跳过 `compact_summary`
3. 默认跳过 `meta`
4. 对 `tool_feedback` 优先提取结论性信息
5. 保留区中的消息不应再次参与当前轮压缩

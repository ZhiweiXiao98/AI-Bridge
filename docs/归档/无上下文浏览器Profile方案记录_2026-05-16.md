# 无上下文浏览器 Profile 计划书

> 文档状态：执行中（2026-05-16 已按当前实现与路线偏差复盘修订）
> 最后编辑日期：2026-05-16
> 适用范围：Data-Bridge 的 API 模式、浏览器模式、Profile 配置、对话级 Profile 选择、上下文编译、GoAmzAI 浏览器主力推理后端适配。

## 1. 背景与目标

当前项目存在两类互补但割裂的模型调用模式：

1. **API 模式**
   - 优点：完全自主可控、可并发、上下文精确、结构化协议稳定。
   - 缺点：成本高，频繁调用时可能产生较大账单压力。

2. **浏览器模式**
   - 优点：可调用网页端顶级模型，推理质量上限高，且在既有账号体系下近似不限量使用。
   - 缺点：上下文托管在网页端，项目无法完全控制；网页 UI 变化会影响稳定性；单个网页会话天然不适合并发。

本计划的核心目标是引入一种新的 Profile 类型：

> **无上下文浏览器 Profile**：将某个 AI 网页对话作为“近似 stateless”的模型后端使用。每一轮请求前，由项目侧编译完整上下文包并发送；每一轮完成后，采集本轮网页回复，并尽量不依赖网页历史上下文继续推理。

这里的“无上下文”不是说网页真的没有任何记忆，而是说 Data-Bridge 不把网页历史当作可信上下文来源。真正的上下文事实仍保存在本地，由项目侧在每轮请求前重新组织。

最终效果：

- 浏览器模式负责主要智能推理、复杂分析、开发主流程与高质量生成。
- API 模式负责可并发的辅助任务、严格结构化处理、工具调度胶水、校验修复和浏览器异常时的工程兜底。
- 上层业务只关心统一的 Profile 调用结果，不关心底层来自 API 还是浏览器网页。
- 设置页只负责 Profile 配置和 fallback 配置的增删改；每个本地对话可以选择自己的 Profile 或 Chain。

### 2026-05-16 当前边界与路线复盘

结论：当前实现仍在原定路径上。现在最重要的不是继续堆浏览器特例，而是把 API 源和浏览器源都收进同一套“上游事件”语言里。

已经走对的部分：

- `browser_stateless` 已作为 API 模式可选 Profile 类型接入。
- 本地 API 对话已支持 `model_usage`，可以按对话选择 Profile 或 Chain。
- 设置页已回到“管理配置”的角色，不再承担每个对话的运行时选择。
- 浏览器 Profile 的目标已从反直觉的 URL 改为 GoAmzAI 左侧会话列表中的“目标对话名称”。
- 浏览器交互已复用现有浏览器模式发送逻辑，不再另建纯文本发送路径。
- 回复读取已改为复用浏览器模式结构化解析链路：`get_chat_content_incremental()`、DOM parser、segments、代码块标记与 transient 解析。
- GoAmzAI 生成期间已支持 transient 临时刷新，最终稳定后再正式写入本地上下文。
- 守护进程配置仍独立，不随对话级 Profile 选择变化。
- 守护进程只使用 API 源，不占用 browser_stateless 这类需要排队的浏览器资源。
- 新增 worker 逻辑主要放在 `app/core/worker_modules`。

正在收口的偏差：

- API Profile 与浏览器 Profile 现在都能作为“上游来源”工作，但还没有统一的上游事件接口。
- 当前已新增薄层 `app/core/worker_modules/upstream_events.py`，开始把两种来源映射为同一组事件语义。
- 当前已新增薄消费入口 `app/core/worker_modules/upstream_consumer.py`，先负责把统一事件转换成现有 UI/worker 信号。
- API stream 已通过 `UpstreamConsumer` 对外发出 started/delta/completed/failed，内部状态机仍监听 `WorkerStreamBridge` 自身信号。
- 浏览器 Profile 已通过 `UpstreamEvent` 生成 started/structured/completed/failed，并由 `UpstreamConsumer` 转换为现有 stream、round、messages、context status 信号。
- 现阶段仍保留 `api_stream_chunk_signal`、`api_stream_status_signal`、`api_round_state_signal` 作为外部兼容通道，后续再统一消费口。

当前路线用一句话概括：

```text
浏览器源继续复用成熟浏览器模式能力；
API 源和浏览器源只在 worker_modules 内部逐步变成同一种上游事件；
UI、上下文、工具闭环先保持可用，再逐步收口；守护进程只监听结果，不占用浏览器 Profile。
```

下一步收口方向：

```text
API Profile
Browser Stateless Profile
Fallback Chain
        ↓
Unified Upstream Events
        ↓
API 对话 UI / 本地上下文 / 工具闭环
```

已新增薄层：

```text
app/core/worker_modules/upstream_events.py
```

该层只定义统一事件，不急于大重构：

```text
started        上游开始
delta          文本增量
structured     结构化片段增量
completed      上游完成
failed         上游失败
diagnostic      诊断信息
```

当前第一步已经完成：API 源与浏览器源的现有 payload 均开始携带 `upstream_event` 语义。

当前第二步已经完成：browser_stateless 和 API stream 均已接入 `UpstreamConsumer`，再由 consumer 转换成现有外部信号。

接下来继续小步推进：先让更多上层消费口读取统一事件语义，但不改 UI、不改远程协议、不改浏览器 DOM 逻辑。

### 2026-05-10 边界修订记录

- **设置页职责**：设置页管理 Profile、Fallback Chain 等配置本身，不再把“当前正在编辑哪个 Profile”直接等同于“所有对话运行时使用哪个 Profile”。
- **对话级选择**：本地 API 对话可通过 `model_usage` 选择 `profile` 或 `chain`。没有对话级选择时，才回退到全局 `api_mode_usage`。
- **守护进程独立**：守护进程和具体对话不是强绑定关系。守护进程暂时只使用 API Profile 或纯 API Chain，不使用 browser_stateless，也不参与浏览器队列和 fallback takeover。
- **浏览器启动顺序**：当前产品可以继续采用“先浏览器、再服务器、再客户端”的常用流程。后续可让服务器和客户端在未打开浏览器时也能启动，但这不是本阶段硬目标。
- **浏览器能力复用**：browser_stateless 不应另起一套简化的文本解析链路。它应复用现有浏览器模式中已经成熟的 DOM 解析、消息同步、代码块绑定、工具调用展示、代码执行入口等能力。
- **JSON 不是默认输出**：网页 AI 默认输出的是富文本、Markdown、代码块和分段 DOM。只有当任务确实需要结构化结果时，才要求它在 Markdown fenced code block 中输出 JSON。解析不到 JSON 时，含义只是“结构化提取失败”，原始回复仍要保留。

目标架构形成：

```text
业务任务
  -> ContextCompiler
  -> BrowserPromptEnvelope
  -> Conversation model_usage / ProfileRouter
  -> Unified Upstream Events
  -> API Profile 或 StatelessBrowserProfile
  -> API token 流 或 现有浏览器消息同步链路
  -> segments / raw_text / Optional StructuredExtractor
  -> 上层会话、代码块、工具循环与 UI
```

## 2. 核心原则

1. **项目侧持有上下文事实**
   - 浏览器网页只作为推理执行器，不作为可信上下文数据库。
   - 历史消息、工具结果、任务状态、知识库摘要都由 Data-Bridge 侧维护。

2. **每轮请求全量自描述**
   - 每次发给浏览器网页的 prompt 必须包含完成本轮任务所需的系统规则、任务目标、必要历史、输入数据和输出要求。
   - 不依赖网页端上一轮对话记忆。

3. **浏览器 Profile 纳入统一配置与调用**
   - 浏览器源不应成为独立分支逻辑，而应实现与 API Profile 相同的运行时调用入口。
   - 成本、延迟、可靠性、并发能力由 Profile 元数据描述。

4. **对话选择和配置管理分离**
   - 设置页负责管理 Profile 与 Chain。
   - 对话负责选择“本对话使用哪个 Profile/Chain”。
   - 全局 `api_mode_usage` 只作为未选择时的默认兜底。

5. **串行能力显式建模**
   - 浏览器 Profile 默认 `supports_parallel = false`。
   - 当前阶段先保证单次请求稳定跑完，不急于设计复杂队列。
   - 后续若要排队或转 API，必须由用户选择的 fallback chain 或显式配置决定，底层不偷偷接管。

6. **API 是工程副驾，不是默认主脑**
   - 网页自动化、输出解析、超时、风控、页面结构变化都必须被视为正常故障类型。
   - API 的价值在于补浏览器短板：并发、结构化、小模型快速处理、工具调用编排、结果校验。

7. **浏览器源只能通过网页消息结构通信**
   - 浏览器源不是可自由收发 JSON RPC 的后端，它只能通过网页聊天输入框发送一段文本或 Markdown。
   - 网页返回也不是原始协议包，而是渲染后的 DOM 消息树。
   - 当前 GoAmzAI 可观察结构以 `chat-item` 为消息单元，依赖 `data-message-id`、`data-message-ai` 区分消息身份和角色。
   - AI 回复正文位于 `.content` / `.chat-text` / `.aa-html` 一类容器下，并被拆成多个 `node-slot`。
   - `node-slot` 通过 `data-node-index` 表示顺序，通过 `data-node-type` 表示渲染块类型，例如 `paragraph`、`heading`、`list`、`code_block`、`blockquote`、`thematic_break`。
   - 因此浏览器 Profile 的真实协议不是“发送结构化请求并收到结构化响应”，而是“发送可渲染 prompt，读取 DOM 渲染结果，再恢复成标准消息”。

8. **不猜 DOM**
   - 浏览器交互必须优先依据 `docs/dom`、`docs/page_outer.html` 和 `docs/GoamzAI平台智能化方案.md` 中的 DOM 契约。
   - 截图只能辅助理解，不作为选择器依据。
   - 新建对话、命名对话、选择模型、上下文携带数、高级设置等隐藏栏能力，后续必须基于真实 DOM 证据实现。

## 3. 目标架构

### 3.1 Profile 抽象

建议在现有 Profile 配置体系中扩展统一模型后端抽象：

```python
class ModelProfile:
    id: str
    name: str
    kind: str  # api | browser_stateless
    provider: str
    model: str | None
    supports_parallel: bool
    cost_level: str  # high | medium | low
    reliability_level: str  # high | medium | low
    max_input_tokens: int | None
    max_output_tokens: int | None
    timeout_seconds: int
```

对应调用接口：

```python
class ModelRequest:
    request_id: str
    task_type: str
    messages: list
    context_bundle: dict
    output_schema: dict | None
    priority: int

class ModelResponse:
    request_id: str
    profile_id: str
    raw_text: str
    structured_message: dict | None
    segments: list
    parsed: dict | None
    usage: dict | None
    finish_reason: str
    diagnostics: dict
```

说明：

- `raw_text` 是从网页消息恢复出来的文本投影，便于兼容 API 模式。
- `segments` 更接近浏览器模式的真实内容，可以保留段落、标题、列表、代码块、引用、工具结果等块信息。
- `parsed` 只是可选的结构化提取结果，不应替代原始消息。

### 3.2 StatelessBrowserProfile

无上下文浏览器 Profile 的职责：

1. 接收统一的 `ModelRequest`。
2. 调用 `ContextCompiler` 生成完整 prompt。
3. 调用 `BrowserPromptEnvelope` 将请求包装成网页聊天框可发送的文本或 Markdown。
4. 驱动浏览器进入指定 AI 网页对话；当前主要通过 GoAmzAI 左侧会话标题定位目标对话。
5. 清理或隔离当前网页对话状态。
6. 输入完整 prompt。
7. 在 GoAmzAI 生成期间，通过浏览器模式 transient 解析链路采集中间态 segments，只刷新 UI，不提前落库。
8. 生成稳定后，通过现有浏览器消息同步链路采集本轮回复，而不是另写简化版 DOM 解析器。
9. 在需要时交给 `Optional StructuredExtractor` 做 JSON/XML 等结构化提取。

内部流程：

```text
ModelRequest
  -> compile_prompt()
  -> build_browser_prompt_envelope()
  -> acquire_browser_lock()
  -> prepare_clean_conversation()
  -> send_prompt()
  -> observe_transient_browser_message()
  -> wait_until_complete()
  -> read_stable_browser_message()
  -> reuse_browser_sync_normalizer()
  -> optional_structured_extract()
  -> release_browser_lock()
```

新 worker 相关逻辑应放在 `app/core/worker_modules`，主 `worker.py` 只保留薄调度入口，避免继续膨胀。

### 3.3 ContextCompiler

`ContextCompiler` 把项目侧状态编译成浏览器网页可理解的完整请求包。

推荐 prompt 结构：

```text
你是 Data-Bridge 的一个近似无上下文推理后端。
本次请求必须只依据下方输入完成任务，不要依赖任何网页历史对话。

<system_rules>
...
</system_rules>

<task>
...
</task>

<context_summary>
...
</context_summary>

<necessary_history>
...
</necessary_history>

<input_payload>
...
</input_payload>

<output_contract>
普通任务：请直接输出自然语言、Markdown、代码块或表格。
结构化任务：请额外把 JSON 放入 ```json fenced block。
</output_contract>
```

关键要求：

- 历史不直接全量塞入，优先使用项目侧摘要与必要片段。
- 对工具循环任务，必须显式给出已执行工具、工具结果、当前轮目标。
- 普通任务不要强迫网页 AI 只输出 JSON，否则会损失浏览器模式原本的富文本和代码块能力。
- 对结构化输出，优先要求 Markdown fenced JSON；解析失败时，记录为“结构化提取失败”，但必须保留原文和标准消息块。
- prompt 需要携带 `request_id`，便于抓取后校验回复是否属于当前请求。
- prompt 最终必须能降级为一段网页输入框可粘贴的纯文本或 Markdown，不能假设浏览器源支持原生多字段请求。

### 3.4 BrowserPromptEnvelope

`BrowserPromptEnvelope` 负责把标准请求包转换成网页聊天框可发送的单段消息。

设计要求：

- 使用明显的边界标签包裹各区域，例如 `<system_rules>`、`<task>`、`<input_payload>`、`<output_contract>`。
- 首尾携带 `request_id`，并要求模型在输出中尽量回显同一个 `request_id`。
- 避免依赖网页端隐藏 metadata，因为浏览器源只能发送可见文本。
- 对大上下文做摘要和片段裁剪，保证一次粘贴可被网页输入框接受。
- 对代码、JSON、日志等内容使用 Markdown fenced code block，降低网页富文本编辑器误解析概率。

示例：

````text
[Data-Bridge Stateless Browser Request]
request_id: req_20260510_001
task_type: architecture_plan

<task>
...
</task>

<input_payload>
```json
{ "...": "..." }
```
</input_payload>

<output_contract>
请用 Markdown 回复。若需要给出机器可读结果，请额外放入 ```json fenced block。
</output_contract>
````

### 3.5 BrowserConversationReset

`BrowserConversationReset` 负责在每轮发送前把网页对话恢复到近似无上下文状态。它不是项目侧的逻辑标记，而是必须真实操作网页 UI。

重要约束：

- “清空”按钮只有在消息窗口置底后才会出现。
- reset 流程必须先滚动消息容器到底部，再查找按钮。
- 不能直接在页面顶部或中间状态查找“清空”，否则会误判按钮缺失。
- 清掉网页聊天记录是允许的，因为可信上下文保存在本地。

当前可观察的清空上下文按钮结构：

```text
button.n-button.n-button--default-type.n-button--tiny-type.n-button--ghost.clickable
  .n-button__icon
  .n-button__content
    span: "清空"
```

建议定位策略：

1. 定位消息滚动容器，例如 `.n-scrollbar-container` / `.n-scrollbar-content`。
2. 将消息窗口滚动到底部，并等待底部工具区渲染完成。
3. 首选语义定位：查找可点击 `button`，其 `.n-button__content` 文本精确等于 `清空`。
4. 辅助特征：按钮包含 `n-button--tiny-type`、`n-button--ghost`、`clickable`。
5. 避免只依赖 `data-v-*` 属性，因为 Vue scoped attribute 可能随构建变化。
6. 点击前记录当前最后一个 `chat-item[data-message-id]`，点击后等待旧消息消失、消息列表归零，或出现明确的空对话状态。
7. 若网页弹出确认框，适配器必须显式确认；若没有确认框，则直接进入清空校验。
8. 清空失败时不得发送本轮 prompt，应返回 `reset_failed`，由调度器决定重试、换浏览器 Profile 或 API takeover。

### 3.6 复用现有浏览器消息同步链路

当前浏览器模式已经具备较完整的消息解析和 UI 绑定能力，包括但不限于：

- 从 DOM 恢复消息、段落、标题、列表、代码块等内容。
- 代码块绑定、代码执行入口、代码块工具按钮。
- `tool_call`、`tool_result`、`ToolCallCard` 等工具循环展示。
- 浏览器同步 normalizer 与上层消息结构衔接。

browser_stateless 应复用这些能力。它新增的是“每轮请求前清空/隔离网页上下文、发送完整 prompt、排队串行调用、按对话选择 Profile”的外层调度能力，而不是重新写一个只能读纯文本的轻量 DOM 适配器。

当前实现已经开始复用这条链路：

- 最终稳定回复：`scan_and_fix_last_message()` 后调用 `get_chat_content_incremental(transient_last_ai=False)`，保留结构化 `segments`。
- 生成中回复：`wait_until_idle(progress_callback=...)` 期间调用 `extract_latest_ai_response(transient=True, require_request_id=False)`，使用浏览器 transient parser 形成临时 segments。
- API 对话落库：最终回复通过 `append_assistant_message(..., segments=..., raw_content=...)` 写入本地上下文。
- 临时刷新：transient 消息只通过 `messages_signal` 推给 UI，不提前写入本地上下文。

当前 GoAmzAI 的可观察 DOM 形态仍然是基础证据：

```text
.chat-item[data-message-id][data-message-ai]
  .content / .chat-text / .aa-html
    .node-slot[data-node-index][data-node-type]
```

建议提取规则：

1. 以 `data-message-id` 作为浏览器侧消息 ID。
2. 以 `data-message-ai="true"` 识别 AI 回复，`false` 识别用户消息。
3. 以最后一个 AI `chat-item` 作为本轮候选回复，再通过 `request_id` 回显做归属校验。
4. 按 `data-node-index` 升序恢复块顺序。
5. 根据 `data-node-type` 恢复块语义：
   - `paragraph` -> 普通文本段落
   - `heading` -> Markdown 标题
   - `list` -> Markdown 列表
   - `code_block` -> fenced code block
   - `blockquote` -> Markdown 引用
   - `thematic_break` -> `---`
6. 原始 DOM 片段只用于诊断，不作为上层长期事实存储。

### 3.7 对话级 Profile 选择与 ProfileRouter

运行时选择顺序建议为：

1. 当前本地对话的 `model_usage`。
2. 全局 `api_mode_usage`。
3. 默认 API Profile。

`model_usage` 支持两种形式：

```json
{ "type": "profile", "ref": "browser_web_primary" }
```

```json
{ "type": "chain", "ref": "primary_browser_then_api" }
```

`ProfileRouter` 根据任务要求选择调用路径。新的默认立场是：

> 对话已经明确选择了某个 Profile/Chain 时，优先尊重对话选择；没有明确选择时，再根据全局默认和任务特征做路由。

建议路由因素：

| 因素 | API Profile | 无上下文浏览器 Profile |
| --- | --- | --- |
| 角色定位 | 工程辅助、副驾、兜底 | 主力推理、开发主流程 |
| 成本 | 高，需要节制 | 极低或近似不限量 |
| 并发 | 强 | 弱 |
| 延迟 | 低 | 中到高 |
| 结构化可靠性 | 高 | 中 |
| 可控性 | 高 | 中低 |
| 模型能力上限 | 取决于 API 配额和可用模型 | 可接入网页端顶级模型 |
| 适合任务 | 并发小任务、严格 JSON、校验修复、工具调度胶水、浏览器异常接管 | 主开发任务、复杂分析、方案设计、代码生成、长文档推理、多轮高质量协作 |

示例策略：

```python
if conversation.model_usage:
    return resolve_conversation_usage(conversation.model_usage)

if request.is_sensitive:
    return local_or_api_profile

if request.requires_many_parallel_subtasks:
    return api_profile

if request.requires_strict_schema and request.is_small_transform:
    return api_profile

if browser_profile.is_healthy and browser_queue.size < main_queue_limit:
    return browser_stateless_profile

if browser_profile.is_unavailable or browser_profile.is_unhealthy:
    return fallback_chain.next_profile()

return wait_for_browser_profile
```

### 3.8 统一上游事件层（下一步收口点）

API Profile 和浏览器 Profile 不应长期在 API 模式内部走两套语义。

当前状态：

- API Profile 仍由 `WorkerStreamBridge` 负责调用真实 API stream；对外发射路径已进入 `UpstreamConsumer`。
- 浏览器 Profile 由 `WorkerBrowserStatelessBridge` 负责调度 GoAmzAI；started、structured、completed、failed 已经通过 `UpstreamConsumer` 发射。
- UI 仍接收旧的 `api_stream_chunk_signal`、`api_stream_status_signal`、`messages_signal`、`context_status_signal`，所以外部表现保持兼容。
- worker_modules 内部已经形成统一上游事件入口，但还没有把 fallback chain 和工具闭环全部收进去。

目标状态：

```python
class UpstreamEvent:
    event: str  # started | delta | structured | completed | failed | diagnostic
    conversation_id: str
    request_id: str
    profile_key: str
    text_delta: str
    accumulated_text: str
    segments: list
    raw_message: dict | None
    diagnostics: dict
```

统一后：

- API token 流转换成 `delta` / `completed`。
- 浏览器 transient DOM 观察转换成 `structured`。
- 浏览器稳定回复转换成 `completed`，携带最终 `segments`。
- fallback chain 只关心事件和错误，不关心底层是 HTTP API 还是网页。
- UI、上下文、工具闭环共用同一个上游事件消费口。
- 守护进程不消费浏览器队列，也不作为 fallback 的接管者。它只在主回复完成后读取结果摘要，并使用自己的 API 源生成建议。

本阶段不要做的事：

- 不把浏览器回复简化成纯文本。浏览器源仍然保留 raw text、segments、代码块和 DOM 解析结果。
- 不要求网页 AI 必须输出 JSON。JSON 只是可选结构化提取，失败时保留原文。
- 不新写一套发送按钮、输入框、多模态附件逻辑。发送仍复用成熟浏览器模式能力。
- 不先做多浏览器并发、新建网页对话、网页隐藏栏模型选择。这些需要 DOM 契约证据补齐后再动。

### Phase 1：最小可用适配器

目标：证明浏览器网页可以被当成一个串行 Profile 调用，并且配置管理与对话选择边界清楚。

任务：

- 新增 `browser_stateless` Profile 类型。
- 设置页支持创建、编辑、删除浏览器 Profile 配置，但不把“正在编辑”强行写成所有对话的运行时选择。
- 本地 API 对话支持保存 `model_usage`，可以选择 Profile 或 Chain。
- 实现单请求串行调用，不考虑并发。
- 支持按 GoAmzAI 左侧会话标题切换目标对话；`conversation_url` 保留为兼容/高级字段，不作为主要用户输入。
- 实现每轮发送前点击网页“清空”按钮。
- 实现清空后校验，确认旧消息不再参与当前网页对话。
- 每轮发送完整 prompt。
- 复用现有浏览器消息同步链路抓取最新 assistant 回复。
- 返回统一 `ModelResponse`。

验收：

- 配置中心可创建、编辑、删除浏览器 Profile 和 fallback Chain。
- 每个本地 API 对话可选择自己的 Profile/Chain。
- 守护进程配置不受对话级选择影响。
- 可以从同一个上层调用接口切换 API Profile 与浏览器 Profile。
- 浏览器 Profile 连续执行 5 轮互不相关任务，回复不依赖前轮网页上下文。
- 单轮失败时不会污染后续任务。
- 能从网页 DOM 中稳定定位本轮 AI 回复消息。
- 清空按钮不可用或清空校验失败时，不会继续发送本轮 prompt。

### Phase 2：上下文编译器与输出规范化

目标：让浏览器 Profile 真正服务于项目上下文，而不是简单转发文本。

任务：

- 实现 `ContextCompiler`。
- 支持任务类型模板：开发主任务、架构分析、代码生成、代码审查、知识库问答、方案生成、总结改写。
- 引入 `request_id`、`task_type`、`output_contract`。
- 复用现有浏览器模式的 Markdown/Segment 恢复链路。
- 对结构化任务实现 JSON/XML 输出提取。
- 对结构化提取实现轻量修复：截取 fenced code block、去除包裹说明、必要时 API assist。
- 生成中 transient 回复只用于 UI 预览，不提前写入本地上下文。
- 稳定回复写回时带 `segments` 与 `raw_content`，避免富文本和代码块被压扁。

验收：

- 普通任务可保留富文本、Markdown、代码块、工具结果等浏览器模式能力。
- 结构化任务尽量返回可解析对象。
- 结构化提取失败时，原始回复和标准消息块仍可被上层使用。
- prompt 中不需要依赖网页历史消息。
- 同一任务分别走 API 与浏览器 Profile 时，上层收到语义一致的响应。

### Phase 3：单次流程稳定与日志观测

目标：先把单条 browser_stateless 请求稳定跑完，并让开发人员能通过中文日志快速判断坏在哪一步。正式队列、取消、健康状态等能力等单次流程稳定后再推进。

任务：

- 为每个浏览器 Profile 增加互斥锁。
- 先不做复杂任务队列，只保留单请求串行保护。
- 暂缓优先级、取消、健康状态。
- 增加统一上游事件层，让 API Profile 与浏览器 Profile 都输出 `started/delta/structured/completed/failed`。
- API assist 属于上游辅助策略，不放在浏览器 Profile 配置里。守护进程只负责轻量建议生成，且只使用 API 源。
- API takeover 只由用户选择的 fallback chain 决定，不按队列长度自动切换。
- 增加中文阶段日志：配置检查、切换目标对话、清空、发送、等待、提取、规范化、落库、失败原因。

验收：

- 单次请求失败时，日志能看出失败阶段和主要参数。
- 单次请求成功时，日志能看到目标对话、prompt 长度、等待耗时、提取消息 id、raw 长度、总耗时。
- fallback chain 接管只在用户选择 Chain 后发生，失败原因以事件和日志形式保留。

## 5. 主力任务与 API 辅助任务

### 浏览器模式应承担的主力任务

- 开发主流程中的复杂分析、架构判断、代码生成与方案设计。
- 需要顶级模型能力的长上下文推理。
- 高质量文档、计划书、审查意见、产品方案、调试判断。
- 需要反复推敲的主对话协作。
- 可排队但质量优先的任务。
- 需要保留 Markdown、代码块、富文本结构的回复。

### API 模式应承担的辅助任务

- 小而快的结构化转换，例如 JSON 修复、字段抽取、格式校验。
- 多路并发的轻量任务，例如批量分类、批量摘要、候选项初筛。
- 工具调用参数生成、工具结果压缩、协议桥接。
- 浏览器网页不可用、队列过长或用户明确要求立即响应时的接管。
- 不适合进入网页端的敏感任务。

### 谨慎进入浏览器模式的任务

- 涉及私钥、账号、付款、内部敏感数据的任务。
- 必须毫秒级响应或强并发的任务。
- 输出协议不可失败且无法二次修复的任务。
- 需要完全自主控制推理上下文和审计链路的任务。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 网页 UI 变化 | 自动化失效 | 选择器版本化、页面状态探测、失败诊断截图 |
| 输出格式不稳定 | 结构化提取失败 | fenced code block、解析修复、必要时 API assist；保留原始回复 |
| 浏览器无法并发 | 队列积压 | 显式队列、优先级、API 分担轻量任务、多 Profile 扩展 |
| 清空按钮定位失败 | 无法进入无上下文状态 | 按文本定位为主、class/图标特征为辅、失败时停止发送并记录诊断 |
| 网页端上下文残留 | 结果受污染 | 每轮真实点击清空或新建对话、清空后校验、完整 prompt、request_id 校验 |
| 账号级记忆或网页策略影响 | 不完全 stateless | 在文档和配置中标记为“近似 stateless”，敏感任务转 API 或本地模型 |
| 风控或限流 | 任务失败 | 请求频率限制、冷却时间、退避重试、健康状态降级 |
| 隐私与合规 | 数据泄露风险 | 敏感任务强制 API 或本地模型，不进入浏览器 Profile |
| 重写浏览器解析链路 | 代码块、工具卡片、执行入口丢失 | 复用现有浏览器模式解析和绑定能力 |

## 7. 配置建议

示例 Profile 配置：

```json
{
  "profiles": {
    "browser_web_primary": {
      "name": "网页 AI 主力 Profile",
      "kind": "browser_stateless",
      "provider": "web_ai",
      "conversation_name": "Web_Profile",
      "conversation_url": "",
      "browser_profile": "current_debug_session",
      "supports_parallel": false,
      "cost_level": "low",
      "role": "primary_reasoning",
      "reliability_level": "medium",
      "timeout_seconds": 180,
      "max_queue_size": 1
    }
  },
  "fallback_chains": {
    "primary_browser_then_api": {
      "profiles": [
        "browser_web_primary",
        "default_api"
      ]
    }
  },
  "api_mode_usage": {
    "type": "profile",
    "ref": "default_api"
  }
}
```

示例对话级选择：

```json
{
  "meta": {
    "model_usage": {
      "type": "profile",
      "ref": "browser_web_primary"
    }
  }
}
```

需要注意：

- `conversation_name` 是普通用户应填写的主字段，含义是 GoAmzAI 网页左侧会话列表里的对话标题。
- `browser_profile = current_debug_session` 是内部连接名，表示使用当前已打开并登录的 GoAmzAI 浏览器页面；普通设置界面应隐藏该字段。
- `conversation_url` 保留为兼容/高级字段，不作为主入口。
- `max_queue_size` 当前建议保持 1，因为单个网页会话天然单工。
- 敏感任务、禁用任务类型应在路由层或统一上游策略层强制执行，不放在浏览器 Profile 内部。
- `role = primary_reasoning` 表示该 Profile 可作为主力模型，不是低优先级备用源。
- API assist 是守护进程/辅助策略的职责；API takeover 是 fallback chain/上游路由职责。
- `api_mode_usage` 是默认兜底，不代表设置页当前选中的 Profile。

  是否转 API 由用户选择的 Chain 决定；底层不根据队列长度自动转 API。

## 9. 优先实现建议

第一步不建议直接追求“完整多网页模型集群”。更稳妥的顺序是：

1. 已完成：设置页 Profile/Fallback 配置管理，不再把设置页选中项当作所有对话运行时选择。
2. 已完成：对话级 `model_usage` 的 UI 选择入口。
3. 已完成：最小 `StatelessBrowserProfileAdapter`，单任务串行，复用浏览器消息结构化解析链路。
4. 已完成：`ContextCompiler` 接入本地 API 上下文系统，保证每轮输入自包含。
5. 已完成大半：普通回复保留富文本/segments；结构化 JSON 仍是可选弱提取。
6. 已完成第一步：新增统一上游事件薄层，让 API Profile 与浏览器 Profile 的 payload 带同一类事件语义。
7. 已完成第二步：统一上游事件消费口；browser_stateless 与 API stream 均已接入 `UpstreamConsumer`。
8. 当前下一小步：先把单次 browser_stateless 请求跑稳，并补齐中文阶段日志，能看懂失败发生在切对话、清空、发送、等待、提取还是落库。
9. 随后推进：让 UI、上下文和工具闭环逐步读取统一事件语义，而不是直接理解 API token 流或浏览器 DOM 观察。
10. 随后推进：fallback chain 只按用户选择工作，记录清楚失败原因；不在底层根据队列长度自动转 API。
11. 暂缓推进：正式队列、取消、健康状态。等单次流程稳定后再做，不提前复杂化工程。
12. 随后推进：路由、API assist、fallback takeover，让浏览器 Profile 成为主力，API 成为工程副驾。
13. 基于真实 DOM 契约补齐网页新建对话、命名、模型选择、上下文携带数等隐藏栏能力。
14. 最后再扩展多个浏览器 Profile。

该方案的本质不是把浏览器网页强行改造成真正 API，也不是把它当成廉价旁路，而是把它提升为 Data-Bridge 的主力推理后端。API 模式保留为工程化副驾：在并发、结构化、校验、工具编排和异常接管上补齐浏览器模式的短板。只要边界清楚，系统就能同时获得网页顶级模型的质量优势，以及 API 模式的可控工程能力。

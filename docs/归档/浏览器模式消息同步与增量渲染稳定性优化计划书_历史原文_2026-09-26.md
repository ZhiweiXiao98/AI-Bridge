# 浏览器模式消息同步与增量渲染稳定性优化计划书

> 最后编辑日期：2026-05-06
> 适用范围：浏览器模式下，服务端从 AI 网页 DOM 抓取对话内容并解析，客户端接收服务端增量更新并渲染对话、代码块、工具调用与工具结果的完整链路。  
> 上游 AI 网页技术栈：前端 Vue3 + NaiveUI，后端 Golang + Gin，数据支持 MySQL 5.7 + Redis。该技术栈属于被浏览器模式抓取和交互的 AI 网页，不属于本项目技术栈；本项目只基于其 DOM 结构、渲染行为和交互特征进行适配设计。

## 1. 背景与目标

当前浏览器模式的问题不是单个 UI 排序 bug，而是多套状态各自维护事实：

- 服务端从浏览器 DOM 做增量抓取和缓存。
- 客户端根据增量结果进行列表 diff 和局部渲染。
- 工具调用、工具结果、代码块绑定依赖 `tool_call_id`、`block_key`、代码内容 fingerprint 等多种线索。
- fixing 阶段代码块会从折叠变为展开，DOM 结构和 HTML 长度会变化，但业务内容未必变化。
- 状态机循环正常，但客户端显示容易出现乱序、用户消息消失、代码块闪烁、工具结果错绑或未绑定。

本计划的目标是把浏览器模式改造成商业软件级稳定链路：

1. 服务端成为唯一事实源。
2. 客户端只消费服务端有序事件并做确定性投影。
3. 消息、segment、代码块、工具调用都有稳定身份。
4. DOM 形态变化不会误判为业务内容变化。
5. 所有增量更新可回放、可去重、可补偿、可测试。

## 2. 核心原则

执行 AI 在改造时必须遵守以下原则：

1. 不用 DOM index 作为长期消息身份。
2. 不用 content hash 作为客户端组件 key。
3. 不用 `outerHTML` hash 直接决定消息内容是否变化。
4. 客户端不自行推断消息顺序，顺序由服务端 `ordinal` 决定。
5. 客户端不自行拼接事实，只通过 reducer 应用 `snapshot + event log`。
6. fixing 阶段必须区分内容变化和 UI 形态变化。
7. 工具结果优先绑定 `tool_call_id`，其次绑定稳定 `segment_id/block_key`，模糊匹配只能作为诊断 fallback。

## 3. 目标架构

```text

  -> Server Canonical Conversation Store
  -> Ordered Event Log
```

## 4. 事件协议设计

### 4.1 事件公共字段

所有服务端下发事件必须包含：

```json
{
  "seq": 1024,
  "conversation_id": "conv_001",
  "round_id": "round_008",
  "event": "message.upsert",
  "created_at": "2026-05-05T10:30:00+08:00"
}
```

字段要求：

- `seq`：本项目服务端/Worker 侧单调递增；若未来接入远端服务，可由远端事件网关或持久化层生成。
- `conversation_id`：对话 ID。
- `round_id`：本轮生成/工具循环 ID。
- `event`：事件类型。
- `created_at`：服务端时间。

### 4.2 主要事件类型

```text

message.upsert
message.patch
message.delete
segment.upsert
segment.patch
segment.delete
tool.status
tool.result
round.state
stream.done
sync.reset
```

## 5. 本项目数据模型建议

当前项目浏览器模式的真实链路是 Python / PySide / Selenium：

- `app/core/driver/browser_js.py`：注入 JS，从上游 AI 网页 DOM 获取 message probe 和 HTML。
- `app/core/driver/browser_incremental.py`：增量解析、缓存、组装消息。
- `app/core/worker.py`：状态机调度、工具执行、通过 `messages_signal` 推送消息。
- `app/ui/pages/chat/message_area.py`：客户端消息列表渲染、增量 diff、工具卡绑定。
- `app/ui/pages/chat/message_area_stream.py`：API 流式临时气泡管理，不是浏览器 DOM 抓取链路的理想模型。

因此执行 AI 不应引入 Go/Gin/MySQL/Redis 作为本项目实现前提。上游 AI 网页的 Vue3 / NaiveUI / Golang / Gin / MySQL / Redis 只用于理解 DOM 结构和动态渲染行为，不是本项目可改造的代码。

## 6. DOM 增量抓取与规范化

### 6.1 Probe 不应只返回 id 和 role

DOM probe 建议返回：

```json
{
  "dom_id": "xxx",
  "role": "AI",
  "dom_index": 12,
  "visible": true,
  "text_len": 530,
  "html_len": 4102,
  "normalized_text_hash": "sha256:...",
  "code_count": 2,
  "ui_state_hint": "expanded"
}
```

这些字段只用于脏检查，不用于最终身份。

### 6.2 分层 hash

必须区分：

```text
dom_hash        DOM 外壳变化，仅诊断或低优先级脏检查
content_hash    规范化后的消息内容变化
segment_hash    单个 segment 的规范化内容变化
ui_state_hash   折叠、展开、加载态、复制按钮等 UI 形态变化
```

代码块折叠变展开时，允许 `dom_hash/html_len/text_len` 变化，但如果解析后的代码内容一致，`code_content_hash` 不应变化。

### 6.3 双 probe 防抖

抓取流程建议：

```text
probe A
fetch changed DOM HTML
probe B
if A != B:
  retry once
if still unstable:
  emit sync.reset or full snapshot
```

这样避免浏览器 DOM 正在 streaming/fixing 时读到半截结构。

### 6.4 无 DOM ID 消息的稳定身份

禁止长期使用 `__idx_3` 作为 message id。

无 DOM ID 时，使用以下线索生成并维护服务端映射：

```text
role
normalized content prefix hash
nearest previous stable message id
first_seen_at
local first_seen uuid
```

index 只能作为临时匹配线索，不能写入客户端协议作为稳定身份。

## 7. 代码块与工具绑定

### 7.1 代码块稳定身份

代码块字段建议：

```json
{
  "segment_id": "seg_msg123_code_0",
  "type": "code",
  "block_key": "msg123:seg_msg123_code_0",
  "code_content_hash": "sha256:...",
  "language": "python",
  "ui_state": "collapsed",
  "rev": 2
}
```

要求：

- `segment_id` 稳定。
- `block_key` 稳定。
- `code_content_hash` 可以变化。
- 不要把内容 fingerprint 放进稳定 `block_key`。

### 7.2 工具调用绑定优先级

绑定优先级：

1. `tool_call_id`
2. `segment_id`
3. 稳定 `block_key`
4. 诊断 fallback：邻近消息 + code ordinal

第 4 项只能用于兜底，并且必须记录日志，后续用于修复协议缺口。

### 7.3 工具状态事件

工具执行状态和结果都应事件化：

```json
{
  "seq": 201,
  "event": "tool.status",
  "conversation_id": "conv_001",
  "round_id": "round_008",
  "tool_call_id": "tc_001",
  "status": "running",
  "message": "正在执行..."
}
```

```json
{
  "seq": 202,
  "event": "tool.result",
  "conversation_id": "conv_001",
  "round_id": "round_008",
  "tool_call_id": "tc_001",
  "success": true,
  "content": "执行完成"
}
```

## 8. 客户端投影模型

### 8.1 Store 结构

当前项目客户端为 PySide UI。建议在 `MessageArea` 外新增一层投影状态，避免继续让 `MessageArea.render_messages()` 直接承担协议、diff、排序和 UI 刷新的全部职责。

```python
@dataclass
class ChatProjectionState:
    last_seq: int = 0
    conversation_id: str = ""
    messages_by_id: dict = field(default_factory=dict)
    ordered_ids: list = field(default_factory=list)
    pending_events: dict = field(default_factory=dict)
    round_state: str = "idle"
```

### 8.2 应用事件规则

客户端 reducer 规则：

```text
if event.seq <= lastSeq:
  drop
if event.seq > lastSeq + 1:
  buffer and request resync
if event.seq == lastSeq + 1:
  apply
  lastSeq = event.seq
  drain buffered events
```

### 8.3 渲染身份规则

客户端组件身份必须使用稳定 ID。当前 PySide 代码中的 `bubbles_cache` 是按列表位置复用气泡，后续应改为按 `message_id` 复用：

```text
bubbles_by_message_id: dict[str, ChatBubble]
ordered_message_ids: list[str]
```

Segment 组件也必须使用稳定 `segment_id` 或稳定 `block_key`：

```text
segment_widgets_by_id: dict[str, QWidget]
```

禁止：

```text
以列表 index 作为消息身份
以 content_hash 作为组件身份
以包含代码内容 fingerprint 的 block_key 作为稳定身份
```

## 9. 流式与 fixing 阶段处理

### 9.1 流式消息不创建独立临时气泡

流式阶段应直接 upsert 同一个 assistant message：

```text
message.upsert(status=streaming)
segment.patch(status=streaming)
segment.patch(status=fixing)
message.patch(status=final)
```

不要在客户端创建临时 streaming bubble 后删除，再等待完整 snapshot 补上。这是消息短暂消失的常见来源。

### 9.2 fixing 阶段刷新策略

fixing 阶段代码块折叠变展开时：

- 如果 `content_hash` 未变，只更新 `ui_state`。
- 如果 `segment.content_hash` 变了，patch 该 segment。
- 如果 segment 数量变化，upsert/delete segment。
- 如果 message ordinal 变化，服务端必须发 `message.reorder` 或完整 snapshot。

### 9.3 防止反复刷新

服务端发送 patch 前做三道判断：

1. 规范化内容 hash 是否变化。
2. `rev` 是否递增。
3. 同一个 `segment_id` 最近短时间内是否已发送相同 hash。

内存缓存或现有状态服务可用于短期去重：

```text
dedupe:{conversation_id}:{segment_id}:{content_hash}
```

## 10. 阶段实施计划

### 阶段一：协议与数据模型

任务：

- 定义事件协议结构。
- 增加服务端 `seq` 生成器。
- 建立 canonical message/segment 模型。
- 增加 snapshot 接口。
- 增加 event log 存储。

验收：

- 任意对话可以返回完整 snapshot。
- 任意事件都有递增 seq。
- 重复事件不会导致状态重复变化。

### 阶段二：浏览器 DOM Normalizer

任务：

- 改造 DOM probe，增加 normalized content hash、segment hash、UI state hint。
- 实现 DOM 到 canonical message 的映射。
- 实现无 DOM ID 消息稳定匹配。
- 实现双 probe 防抖。

验收：

- fixing 阶段代码块折叠/展开不会改变 message id。
- 用户消息不会因 DOM index 变化而消失。
- 内容未变时不发送内容 patch。

### 阶段三：事件投递层

任务：

- 在 Worker 侧提供统一事件出口，优先复用 Qt Signal。
- 支持 `since_seq` 语义或等价的 snapshot 补偿。
- 支持缺口时下发 `sync.reset` 或客户端主动拉 snapshot。
- 内存保存近期事件，必要时复用现有状态服务保存快照。

验收：

- 客户端断线重连后能补齐事件。
- 乱序、重复、缺失事件有确定处理。

### 阶段四：PySide 客户端 reducer

任务：

- 建立 `messagesById + orderedIds` 投影。
- 替换基于数组 index 的列表 diff。
- `ChatBubble` 以 `message_id` 为身份。
- Segment 以 `segment_id` 为身份。
- 工具卡以 `tool_call_id` 为身份。

验收：

- 消息新增、更新、删除、重排都不造成用户消息消失。
- 相同内容重复事件不会重复渲染。
- 工具结果能稳定更新对应工具卡。

### 阶段五：工具回流与代码块稳定绑定

任务：

- 拆分 `block_key` 和内容 fingerprint。
- 工具调用输出稳定 `tool_call_id`。
- 工具结果事件化。
- 模糊绑定仅作为 fallback 并打诊断日志。

验收：

- fixing 阶段代码块内容变化不会导致工具卡丢失。
- 工具执行完成后结果稳定回填到对应卡片。
- 工具结果消息不会错误隐藏正常内容。

### 阶段六：回归测试与观测

任务：

- 增加服务端 reducer 回放测试。
- 增加客户端 reducer 单元测试。
- 增加 DOM fixture 测试。
- 增加端到端测试场景。
- 增加协议诊断日志和 debug 面板。

验收：

- 支持回放一段事件日志复现 UI 状态。
- 支持导出 snapshot + events 供问题定位。
- 高频 fixing/streaming 下无消息消失和错序。

## 11. 必测场景清单

执行 AI 必须覆盖以下测试：

1. 用户发送消息后，AI streaming 前用户消息不消失。
2. AI streaming 多次 patch，最终消息不重复。
3. fixing 阶段代码块从折叠变展开，内容不变时不重建 bubble。
4. fixing 阶段代码内容变化，只 patch 对应 segment。
5. DOM 节点无 data id，前面插入一条消息后身份仍稳定。
6. 工具调用开始、运行、完成，状态稳定更新同一张工具卡。
7. 工具结果晚于 assistant final 到达，仍能绑定。
8. 事件通道中断后，通过 snapshot 或 `since_seq` 语义补齐。
9. 事件重复到达，客户端丢弃。
10. 事件乱序到达，客户端缓存并按序应用。
11. 缺失事件，客户端触发 snapshot resync。
12. Worker 或 UI 状态重置后，能通过完整 snapshot 恢复当前对话显示。

## 12. 执行约束

执行 AI 在落地时应遵守：

- 每个阶段独立提交，避免一次性大爆炸改造。
- 每个阶段保留兼容层，直到新链路验证稳定。
- 对现有 API 模式逻辑只借鉴，不破坏。
- 不要为了快速修复继续增加客户端猜测逻辑。
- 所有新事件结构必须有单元测试。
- 所有 DOM normalizer 规则必须有 fixture。
- 所有关键状态转换必须有日志：`conversation_id`、`round_id`、`seq`、`message_id`、`segment_id`。

## 14. 成功标准

该任务完成后，应达到：

- 浏览器模式下用户消息不再偶发消失。
- 对话排序完全由服务端 `ordinal` 控制。
- 客户端能够处理乱序、重复、缺失事件。
- fixing 阶段 DOM 展开/折叠不导致内容反复刷新。
- 代码块和工具调用稳定绑定。
- 问题可通过 snapshot + event log 回放定位。

一句话目标：客户端不再猜状态，只投影服务端的有序事实。

## 附录 B：事件缓存与 Snapshot 补偿机制

### B.1 服务端缓存

`BrowserCanonicalStore` 维护以下内存状态：

- `messages_by_id`：按 message_id 索引的完整 canonical 消息
- `ordered_ids`：按 ordinal 排列的 message_id 列表
- `segments_by_id`：按 segment_id 索引的完整 canonical segment
- `recent_events`：最近 200 条事件日志（`deque(maxlen=200)`）
- `last_seq`：最新事件的 seq

### B.2 Snapshot 补偿流程

```
客户端检测到 seq 跳跃
  → reducer 触发 resync callback
  → 客户端请求完整 snapshot（当前实现：Worker 下一轮推送自动包含完整 snapshot）
  → reducer 用 snapshot 替换全部投影状态
  → last_seq 更新为最新 seq
```

当前阶段简化实现：Worker 每轮推送都是完整 `conversation.snapshot`，客户端不需要主动拉取。未来可优化为增量推送 + 按需 snapshot。

### B.3 事件去重

- **服务端**：`BrowserCanonicalStore.upsert_message` 检测 `content_hash + rev` 不变 → 返回 False
- **客户端**：`ChatProjectionReducer.apply_messages` 检测 `seq <= last_seq` → 返回 `stale`

### B.4 乱序处理

当前阶段简化策略：seq 跳跃超过阈值（5）时触发 resync，未实现事件缓冲排序。理由是当前 Worker 是单线程推送，乱序概率极低。未来如需支持多线程事件源，需增加 pending_events 缓冲和按序排空逻辑。

## 17. Canonical ID 含 role + 工具绑定闭环修复

> 创建日期：2026-05-05
> 状态：✅ 已完成

### 17.1 问题分析

#### 问题 A：Canonical ID 不含 role → 同 DOM ID 的 User/AI 消息碰撞

**链路**：
```
DOM data-message-id="5921814" 包含 User + AI 两条消息
→ BrowserMessageCache 用 "5921814:User" / "5921814:AI" 区分 ✅
→ raw_msgs 两条，id 都是 "5921814"，role 分别是 User / AI
→ Normalizer._resolve_stable_id("5921814", role="User") → 直接 return "5921814" ❌
→ Normalizer._resolve_stable_id("5921814", role="AI")  → 直接 return "5921814" ❌
→ 两条消息 canonical ID 相同
→ Store.messages_by_id["5921814"] = AI消息（覆盖 User消息）
→ ordered_ids = [5921814, 5921814, ...]（重复）
→ 10 条 User 消息全部丢失
```

**日志证据**：
```
[CanonicalStore] snapshot 应用 | msgs=20 | ids=[5921814 | 5921814 | 5921816 | 5921816 | ...]
[ProjectionReducer] 应用完成 | added=10 | updated=10  ← 应该是 added=20
```

#### 问题 B：工具绑定失败 — ToolCallCard 和 tool_result 的 key 对不上

**链路**：
```
1. code segment (tool_call)：
   - DOM 提取时没有 tool_call_id（只有执行时才生成）
   - Normalizer 生成 block_key = "5921814:0"
   - ChatBubble 注册 key = block_key = "5921814:0"

2. tool_result segment：
   - DOM parser 从 [TOOL_RESULT_META] 提取 tool_call_id = "toolcall_ddf6154b"
   - DOM parser 也提取了 block_key，但 Normalizer 在 _normalize_segment 中
     对非 code 类型强制设 block_key = None → 丢失了！
   - ChatBubble._tool_result_boxes_by_id 的 key = tool_call_id

3. _try_cross_message_tool_binding 查找：
   - tool_call_id 查注册表 → 失败（注册表只有 block_key 格式）
   - block_key 查注册表 → 失败（tool_result 的 block_key 被 Normalizer 丢了）
   - fuzzy 查找 → 失败（没有 block_key 无法解析 code_index）
   → 绑定失败
```

**日志证据**：
```
[ChatBubble-诊断] ToolCallCard注册 | reg_key=5921814:0 | tool_call_id= | block_key=5921814:0
[绑定-诊断] 绑定失败 | tool_call_id=toolcall_ddf6154b | block_key= | 注册表keys=['5921814:0', ...]
```

### 17.2 修复方案

#### P1：Canonical ID 始终含 role

**改动**：`normalizer.py` → `_resolve_stable_id`

```python
# 之前
if raw_id:
    return raw_id

# 之后
if raw_id:
    return f"{raw_id}:{role}"
```

fallback ID 同理：
```python
# 之前
stable_id = f"msg_fb_{ordinal}_{fallback_hash}"

# 之后
stable_id = f"msg_fb_{ordinal}_{fallback_hash}:{role}"
```

**效果**：
- `"5921814"` → `"5921814:User"` / `"5921814:Assistant"`
- `"msg_fb_1_abc12345"` → `"msg_fb_1_abc12345:User"`

**下游自动联动**（无需额外改动）：
- `block_key` 自动变成 `"5921814:Assistant:0"`（因为 `block_key = f"{message_id}:{code_ordinal}"`）
- `segment_id` 自动变成 `"seg_5921814:Assistant_code_0"`
- Store / Projection / message_area 全部用 `msg.id` / `mid` 做字典 key，透明兼容
- Worker → Executor → `[TOOL_RESULT_META]` 闭环：Worker 从 canonical segment 读 `block_key`，写入浏览器，Parser 读回 → 格式一致

**需额外改动**：
- 测试用例中硬编码的 ID 断言

#### P2：Normalizer 保留 tool_result 的 block_key + 双向注册

**根因**：Normalizer `_normalize_segment` 对非 code 类型强制 `block_key = None`，丢弃了 DOM parser 提取的 `block_key`。

**改动 1**：`normalizer.py` → `_normalize_segment`

```python
# 之前
block_key = f"{message_id}:{code_ordinal}" if seg_type == "code" else None

# 之后
if seg_type == "code":
    block_key = f"{message_id}:{code_ordinal}"
elif seg_type == "tool_result":
    block_key = seg_raw.get("block_key")  # 保留 DOM parser 提取的 block_key
else:
    block_key = None
```

**改动 2**：`chat.py` → ChatBubble 渲染 ToolCallCard 时，同时用 `tool_call_id` 和 `block_key` 注册

```python
# 之前（_try_build_tool_call_box_from_code_seg 路径）
reg_key = tool_call_id or block_key
if reg_key:
    self._tool_cards_by_id[reg_key] = tool_call_box

# 之后
if block_key:
    self._tool_cards_by_id[block_key] = tool_call_box
if tool_call_id:
    self._tool_cards_by_id[tool_call_id] = tool_call_box
```

同理，`tool_call` 类型 segment 的注册也改为双向：
```python
# 之前
if tool_call_id and isinstance(box, ToolCallCard):
    self._tool_cards_by_id[tool_call_id] = box

# 之后
if isinstance(box, ToolCallCard):
    if tool_call_id:
        self._tool_cards_by_id[tool_call_id] = box
    _bk = str(seg.get('block_key') or '').strip()
    if _bk:
        self._tool_cards_by_id[_bk] = box
```

**效果**：
- ToolCallCard 同时注册 `tool_call_id` 和 `block_key` 两个 key
- tool_result 有 `block_key` 后，绑定查找 `block_key` → 命中
- tool_result 有 `tool_call_id` 后，绑定查找 `tool_call_id` → 命中
- 双保险，任一 key 匹配即可绑定成功

#### P2 补充：tool_result 的 block_key 兜底推导

**场景**：历史对话中 DOM 里的 `[TOOL_RESULT_META]` 可能没有 `block_key`（旧版本写入的），或者 `block_key` 是旧格式（`5921814:0` vs 新格式 `5921814:Assistant:0`）。

**改动 3**：`normalizer.py` → `_normalize_segment` 中，tool_result 的 block_key 兜底逻辑

```python
elif seg_type == "tool_result":
    block_key = seg_raw.get("block_key")
    if not block_key and tool_call_id:
        # 无 block_key 时，在同消息的 code segment 中查找匹配的 tool_call_id
        # 由 _normalize_one 在全部 segment 处理完后回填
        block_key = None  # 标记为待回填
```

**改动 4**：`normalizer.py` → `_normalize_one` 末尾增加回填逻辑

```python
# 在所有 segment normalize 完成后
# 建立 tool_call_id → block_key 的映射
code_block_map = {}  # tool_call_id → block_key
for seg in segments:
    if seg.type == "code" and seg.tool_call_id and seg.block_key:
        code_block_map[seg.tool_call_id] = seg.block_key

# 回填 tool_result 的 block_key

```

**效果**：即使 DOM parser 没有提取到 `block_key`，也能通过 `tool_call_id` 在同消息内找到对应的 code segment 的 `block_key`。

- Normalizer 对 `tool_call` 类型 segment 也保留 block_key（与 tool_result 同等处理）
- 这样工具反馈消息中 tool_call + tool_result 成对出现，精确匹配优先，位置匹配兜底

## 18. 服务端绑定闭环 + 用户消息识别 + 三级兜底

> 创建日期：2026-05-05
> 状态：✅ 代码已完成，待运行验证

### 18.1 问题分析

#### 问题 A：工具块和工具结果显示在用户端，未绑定到 AI 端工具块

**现象**：
- AI 端 ToolCallCard 显示"调用工具: unknown"，参数区域显示"（无参数）"，下方无工具结果
- 用户端 ToolCallCard 显示"调用工具: unknown"，参数区域显示"（无参数）"，下方有工具结果
- 工具回流消息（role=User, 含 TOOL_RESULTS_BEGIN）被渲染为用户气泡

**根因**：
1. `tool_call_id` 在工具执行时才生成，AI 消息首次推送到客户端时 segment 没有 `tool_call_id`，ToolCallCard 无法通过 `tool_call_id` 注册
2. 绑定逻辑在客户端 `_try_cross_message_tool_binding` 中执行，依赖客户端猜测匹配，违反 §2.5 "客户端不自行拼接事实"原则
3. 工具回流消息在 AI 网页上是用户发送的消息，但本质上不应渲染为用户气泡

#### 问题 B：`[USER_MESSAGE_BEGIN]...[USER_MESSAGE_END]` 未正确识别

**现象**：用户追加消息（如"不要发了"）被包裹在工具回流文本中，未拆分显示为独立用户气泡

**根因**：DOM Parser 的 `_split_tool_feedback_text_segment` 只解析 `[TOOL_RESULTS_BEGIN]...[TOOL_RESULT_END]`，不识别 `[USER_MESSAGE_BEGIN]...[USER_MESSAGE_END]` 标记

### 18.2 修复方案

#### 核心设计：绑定从客户端移到服务端

```
旧链路（客户端绑定）：
  DOM → raw_msgs → normalizer → 推送 → 客户端猜测匹配

新链路（服务端绑定）：
  DOM → raw_msgs
    → 预扫描：tool_call_id 提前生成 + 回写
    → normalizer：_normalize_one (segment 携带 tool_call_id)
    → normalizer：_bind_tool_feedback_to_ai (服务端绑定)
        → tool_result 匹配到 AI tool_call segment → _bound_results
        → user_message 提取为独立 CanonicalMessage
        → 工具回流消息标记 _hidden / 兜底降级
    → 推送：segments 含 _bound_results, 消息含 _hidden
    → 客户端：跳过 _hidden → 消费 _bound_results → 渲染 user_message
```

#### 修改 1：`tool_call_id` 提前生成 + 回写

**文件**：`app/core/tool_runtime/segment_parser.py`

- `parse_segments` 新增 `write_back_tool_call_id` 参数

#### 修改 3：normalizer 服务端绑定 + 三级兜底

**绑定全部失败**（第三轮兜底后仍有 unmatched）：

### 19.1 当前仍未解决的问题

#### P1-1：无 DOM id 消息仍不会按内容变化失效缓存

**位置**：`app/core/driver/browser_incremental.py:257-303`

当前实现只给有 `item_id` 的消息记录 `current_content_sigs`，并且只有 `item_id` 存在时才比较 `old_sig/new_sig`。缺少 DOM id 的消息仍走 `__idx_i` 缓存，同一位置内容变化不会触发重新抓取。浏览器模式一旦上游 DOM 不给稳定 id，旧内容、用户消息消失或显示旧消息问题仍可能复现。

**修复要求**：
- 内容签名 key 必须与实际缓存 key 对齐：有 DOM id 使用 `message_id:role`，无 DOM id 使用 `__idx_i`。
- 无 DOM id 消息也必须参与 `text_len:html_len:code_count` 签名比对。
- 结构变化、插入、删除时应优先降级全量或至少刷新受影响窗口，避免 `__idx_i` 错位复用。

#### P1-2：内容签名在抓取成功前被推进

**位置**：`app/core/driver/browser_incremental.py:293-350`

检测到内容签名变化后，代码立即把 `_last_content_sigs` 更新为 `current_content_sigs`，然后才执行 `CHAT_CONTENT_BY_INDEX` 并解析。如果这次定向抓取失败、`fetched` 缺失或 `parse_single_message` 返回空，旧缓存仍在，但签名已经变成新值；下一轮会误判无变化，永久跳过重试。

**修复要求**：
- `_last_content_sigs` 只能在对应 index 抓取并解析成功、缓存写入成功后提交。
- 抓取失败的 index 应保留旧签名，并在下一轮继续判定为 changed。
- 如果定向抓取返回不完整，应降级全量抓取或标记 dirty retry。

#### P1-3：增量 upsert 未更新 ordinal/index 导致排序错误

**位置**：`app/core/browser_sync/projection.py:105-111`

Normalizer 在内容不变时会复用缓存对象并更新 `ordinal`，Worker 又会把这些 tail 消息作为 `message.upsert` 发出。但 `ChatProjectionReducer` 只有 `content_hash/rev` 变化才替换 existing，因此 ordinal/index 变化会被忽略。

**修复要求**：
- `ProjectionReducer` 必须把 `ordinal`、`index`、`role`、`conversation_id` 等投影关键字段变化也视为状态更新。

## 21. 2026-05-06 修复记录：流式代码块半成品缓存冻结
> 修复日期：2026-05-06
> 修复范围：`browser_incremental.py`、`parser.py`、`tests/test_browser_sync.py`

### 21.1 问题现象

当 AI 正在输出代码块时，如果服务端恰好抓取到半截代码块，缓存中会写入这份半成品。后续同一条尾部 AI 消息可能因为缓存保护和内容签名推进，被误认为已经稳定，导致客户端代码块长期停在半截内容或“正在输出”状态。

### 21.2 根因

1. `browser_incremental.py` 中的 transient 缓存保护只要发现已有 `block_key` 的代码块，就会跳过 transient 重解析，半成品代码块有机会阻止后续刷新。
2. 流式尾部 AI 消息抓取成功后会推进 `_last_content_sigs`，使这次半成品签名变成稳定签名，收尾 idle 时可能不再强制抓取最终 DOM。
3. `parser.py` 对 transient code preview 设置了过小阈值，长代码块会被替换成 `code_placeholder`，不利于客户端展示正在增长的真实代码内容。

### 21.3 修复方案

1. 移除“已有代码块则跳过 transient 重解析”的缓存保护，流式尾部 AI 消息每轮都允许用当前 DOM 覆盖缓存。
2. 对 `transient_last_ai=True` 的最后一条 AI 消息，不提交 `_last_content_sigs`。这样 AI 收尾进入 idle 后，下一轮会继续判定为 changed，并抓取最终稳定版。
3. 放宽 transient code preview 规则：只要能提取到非空代码，就作为 `code` segment 输出，并保留 `is_transient_preview=True` 标记，不再因代码较长退化为占位符。

### 21.4 验证结果

已新增回归测试：
- 长流式代码块输出为 `code` segment，而不是 `code_placeholder`。
- 缓存中已有旧代码块时，流式尾部抓取仍会刷新为最新代码。
- 流式尾部抓取成功后不会推进稳定内容签名，确保收尾后仍会抓取最终版。

## 22. 2026-05-06 修复记录：工具回流顺序兜底误绑定普通代码块
> 修复日期：2026-05-06

### 22.1 问题现象

以下路径均改为只使用真实工具调用锚点：
- `tool_call_id` 精确匹配表
- `block_key` 精确匹配表
- 顺序匹配兜底中的前序 AI 未绑定锚点列表
- 同消息内 tool_result 的 block_key 补齐逻辑

普通 `python/javascript/markdown/code` 代码块不再接收工具结果。

## 23. 2026-05-06 修复记录：重启后长工具调用代码块身份丢失
> 修复日期：2026-05-06
> 修复范围：`parser.py`、`segment_parser.py`、`normalizer.py`、`chat.py`、`tests/test_browser_sync.py`

### 23.1 问题现象

重启客户端后，历史工具回流消息没有稳定绑定到上一条 AI 消息的工具执行代码块。部分较长的工具调用 JSON 还会显示为普通代码块，而不是专属 ToolCallCard 样式。

### 23.2 根因

上一轮为修复“流式代码块半截冻结”，放宽了 transient code preview：长代码也会立即以 `code` segment 推送。这一方向本身是必要的，但遗漏了工具调用 JSON 的二次识别：

- 流式阶段如果 DOM header 没有稳定识别为 `tool_call`，长工具调用 JSON 会以普通 `code` 进入缓存。
- `_prescan_tool_call_ids()` 只识别 `language == "tool_call"` 的代码块，因此不会给这类普通 `code` 生成 `tool_call_id`。
- `normalizer` 只能依赖顺序兜底，服务端日志可能显示绑定成功，但客户端没有稳定 ToolCallCard 身份。
- UI 侧 `_try_build_tool_call_box_from_code_seg()` 也只看 `language == "tool_call"`，导致长工具调用 JSON 被渲染为普通 CodeBox。

### 23.3 修复方案

统一工具调用 JSON 识别规则：代码内容若能解析为 JSON object，且包含 `name` 与 `arguments`，则视为工具调用。

改动点：
- `parser.py`：transient code preview 中识别工具调用 JSON，并将 `language` 修正为 `tool_call`。
- `segment_parser.py`：预扫描时即使 `language` 缺失，只要内容是工具调用 JSON，也生成 `tool_call_id` 并回写 `language=tool_call`。
- `normalizer.py`：规范化时将工具调用 JSON code 提升为 `language=tool_call`，并允许带 `tool_call_id` 的工具调用 JSON 作为绑定锚点。
- `chat.py`：UI 渲染 ToolCallCard 时，除 `language=tool_call` 外，也允许带 `tool_call_id` 或 `_bound_results` 的工具调用 JSON code 渲染为 ToolCallCard。

### 23.4 验证结果

新增回归测试：
- 预扫描能把无 language 的工具调用 JSON code 提升为 `tool_call` 并写入 `tool_call_id`。
- normalizer 能把无 language 的工具调用 JSON code 提升并绑定 tool_result。
- parser 在 transient 阶段能把工具调用 JSON 标为 `language=tool_call`。

# 一、背景与问题

## 1.1 原始链路（已优化前）

```
主循环 (0.3s)
  ├─ _browser_detect_state()       # is_busy() 金指标检测
  ├─ _browser_process_messages()   # 每轮都执行
  │    ├─ get_chat_content()       # 全量 DOM 提取
  │    │    ├─ find_elements()     # 1 次 IPC
  │    │    └─ 逐元素提取          # 每元素 4-6 次 IPC
  │    │         ├─ el.size["height"]        # IPC
  │    │         ├─ el.get_attribute("outerHTML")  # IPC（最重）
  │    │         ├─ el.text                  # IPC
  │    │         ├─ el.get_attribute("data-message-ai")  # IPC
  │    │         └─ el.get_attribute("data-message-id")  # IPC
  │    ├─ BeautifulSoup 解析       # 每元素 1 次
  │    ├─ process_images()         # 图片本地化
  │    ├─ tag_messages()           # 打索引标记
  │    ├─ raw_len 变化检测         # sum(raw_len) 比对
  │    └─ messages_signal.emit()   # 全量推送给 UI
  └─ 流水线结束后
       └─ _emit_browser_messages_snapshot()  # 又一次全量抓取 + 无条件 emit
```

## 1.2 当前链路（阶段 1+3 已落地）

```
主循环 (0.3s)
  ├─ _browser_detect_state()       # is_busy() + 状态机事件驱动
  ├─ _browser_process_messages()   # 状态机驱动推送决策
  │    ├─ IDLE → _idle_probe_and_maybe_push()
  │    │    ├─ get_chat_content_incremental()  # 增量提取
  │    │    │    ├─ CHAT_CONTENT_PROBE  # 1 次 IPC，~2KB，返回 [{id, ai}, ...]
  │    │    │    ├─ 结构对比 (id, ai) 有序列表 vs 上轮
  │    │    │    ├─ 无变化 → 静默跳过（0 次 BS4）
  │    │    │    └─ 有变化 → 定向提取 + 缓存更新
  │    │    └─ has_structural_change=False → 零推送
  │    ├─ 非 IDLE → _do_extract_and_push()
  │    │    ├─ get_chat_content_incremental()  # 增量提取
  │    │    └─ _do_push_extracted_messages()   # process_images → deduce_state → tag → emit
  │    └─ 状态机事件驱动缓存失效（PIPELINE_END 时 invalidate_message）
  └─ 流水线结束后
       └─ _emit_browser_messages_snapshot()  # 增量提取 + 状态机驱动缓存失效
```

# 二、平台技术约束

基于 `docs/GoamzAI平台智能化方案.md`：

| 约束 | 影响 |
|------|------|
| NaiveUI NVirtualList 虚拟滚动 | 离屏消息 DOM 可能被回收，`find_elements()` 不一定返回全部消息 |
| Monaco Editor 视口渲染 | 代码块只渲染可见行，折叠代码块需要 AutoFix 展开 |
| `data-message-id` 属性 | 稳定可靠，作为缓存 key 的主字段 |
| `data-message-ai` 属性 | 稳定可靠，标识 AI/User 角色，参与 cache_key 组成 |
| CDP 已开启 | `execute_script` 可用于批量 JS 调用 |
| `--disable-backgrounding-occluded-windows` | 已配置，最小化时 DOM 仍可用 |

**关键约束**：虚拟滚动意味着 DOM 元素会被回收/重建，缓存 key 不能依赖 DOM 元素引用。实际实现用 `message_id:role` 作为 cache_key，不依赖 html_len。

# 四、方案设计

## 4.1 JS 批量提取（消除 IPC 瓶颈）— ✅ 已实现

实际实现与原方案的差异：

| 原方案 | 实际实现 | 差异原因 |
|--------|----------|----------|
| JS 脚本放在 `config.py` | JS 脚本放在 `browser_js.py`，选择器从 config.py 导入 | 单一职责，JS 脚本集中管理 |
| 选择器 `.chat-item, .message, .ds-text` | 选择器 `.chat-item` | 实测只有 `.chat-item` 有效，其他匹配数为 0 |
| probe 返回 `{id, len}` | probe 返回 `{id, ai}` | 用 (id, ai) 有序列表做结构变化判定，比 len 更准确 |
| batch 返回 `{id, ai, html, len}` | batch 返回 `{id, ai, html}` | 去掉 len 字段，不再用内容指纹做命中判断 |
| `CachedMessage` 含 `html_len` | `CachedMessage` 不含 `html_len` | cache_key = `message_id:role`，不依赖内容指纹 |

### 已实现的 JS 脚本

- **BATCH_CHAT_CONTENT**：全量提取，1 次 IPC，返回所有可见消息的 id/ai/html
- **CHAT_CONTENT_PROBE**：轻量探测，1 次 IPC，~2KB，返回所有可见消息的 id/ai
- **CHAT_CONTENT_BY_INDEX**：定向提取，1 次 IPC，只返回指定索引的元素

### 已实现的缓存架构

```python
# browser_cache.py
@dataclass
class CachedMessage:
    message_id: str
    role: str
    segments: list
    raw_len: int

class BrowserMessageCache:
    # cache_key = f"{message_id}:{role}"
    # 同一 data-message-id 下 User 和 AI 是两条不同消息
    # 状态机事件驱动失效：invalidate_message(message_id)
```

### 已实现的增量流程

```
1. execute_script(CHAT_CONTENT_PROBE)
   → [{id, ai}, ...] （1 次 IPC，~2KB）

2. 构建 (id, ai) 有序列表 vs 上轮 _last_probe_keys 对比
   → has_structural_change

3. 对缓存未命中的索引 execute_script(CHAT_CONTENT_BY_INDEX, [indexes])
   → 只提取变化的元素（1 次 IPC）

4. BS4 解析变化的元素，更新缓存

5. 组装完整消息列表 + has_structural_change 返回
```

### 各状态下的实际行为

| 状态 | 行为 | IPC 次数 | BS4 解析次数 |
|------|------|---------|-------------|
| 空闲（无变化） | probe → 结构无变化 → 静默跳过 | 1 | 0 |
| AI streaming | probe → 缓存未命中最后 1 条 → 定向提取 | 2 | 1 |
| 新消息追加 | probe → 发现新条目 → 定向提取 | 2 | 1-2 |
| 会话切换 | 全量提取（缓存清空） | 1（batch JS） | N |
| fixing（代码块展开） | probe → 缓存未命中变化条目 → 定向提取 | 2 | 1-3 |

## 4.3 稳定快照收口 + changed:38 优化 — ✅ 已实现

### 实际实现方式（与原方案不同）

| 原方案 | 实际实现 | 差异原因 |
|--------|----------|----------|
| 修改 `_segments_changed` 剥离 HTML 比对 | 删除 `_segments_changed`，改用 `_structural_diff` | 根本性解决：不再比 segments 内容，只比 id+role |
| 过滤 `code_placeholder` 类型 | 不需要，因为不再比 segments | 同上 |
| `_emit_browser_messages_snapshot` 用增量缓存 | ✅ 已改用 `get_chat_content_incremental` | 一致 |
| 移除 `raw_len` 变化检测 | ✅ 已移除 `sum(raw_len)` 比对 | 改为缓存驱动 |

`_structural_diff` 的设计思路：
- 只比 `(id, role)` 有序对，不比 segments 内容
- 结构无变化 → 跳过渲染（返回 None）
- 结构有变化 → 滑动窗口增量渲染（drop_head + update_from）
- 彻底绕过了 transient→stable 的内容 diff 问题

**副作用（阶段 3 引入的回归）**：AI_STREAMING 时，AI 消息 id 不变但 segments 内容在持续变化，`_structural_diff` 返回 None 导致流式更新被吞掉。需阶段 4 修复。

## 4.4 AI_STREAMING 流式渲染回归 — ❌ 待实施

### 问题

阶段 3 用 `_structural_diff` 替代 `_segments_changed` 解决了 changed:38，但引入了回归：

```
AI_STREAMING 期间：
  Worker: 每轮推送消息（AI 内容在变）→ messages_signal.emit
  UI: _structural_diff 只比 (id, role) → AI 消息 id 没变 → 返回 None → 跳过渲染
  结果：AI 流式输出在 UI 上不可见
```

`render_messages` 已接受 `round_state` 参数，`page.py` 已传递 `browser_round_state`，但函数体里完全没用到它。

### 方案：AI_STREAMING 时绕过结构 diff，走轻量流式更新

```python
def render_messages(self, messages, incoming_id, force_scroll=False, round_state=None):
    # ... 对话切换检测 ...
    
    if round_state == 'ai_streaming':
        # AI 流式期间：只更新最后一个 AI 气泡的内容
        return self._streaming_update(messages)
    
    # 非 AI_STREAMING：走结构 diff
    result = self._structural_diff(messages)
    if result is None:
        return False
    # ... 增量渲染 ...
```

`_streaming_update` 的逻辑：
1. 找到 messages 中最后一条 role='AI' 的消息
2. 在 bubbles_cache 中找到对应的 ChatBubble
3. 调用 `b.update_content(msg_data)` 更新内容
4. 更新 `_last_rendered_messages` 快照
5. 节流：300ms 内不重复更新（避免每轮轮询都刷 UI）

### 节流设计

Worker 侧 AI_STREAMING 每轮（~0.3s）都推送，但 UI 不需要这么频繁地更新：
- 设 `_last_streaming_update_time`，300ms 内的重复推送直接跳过
- 这样 Worker 侧数据始终最新（缓存不丢），UI 侧约 3 次/秒更新（足够流畅）

## 4.5 block_key 稳定性 + 工具绑定修复 — ❌ 待实施

### 问题（来自 HANDOFF_2026-05-03_block_key.md）

```
因果链：
1. AI 回复 → AutoFix 展开折叠代码块
2. AutoFix 前: block_key = "5906181:0:a1b2c3d4" (PRE_FIX)
3. ToolCallCard 注册 reg_key = "5906181:0:a1b2c3d4"
4. AutoFix 后: 代码块内容从折叠变为完整 → code_fp 变化
5. AutoFix 后: block_key = "5906181:0:e5f6g7h8" (POST_FIX)
6. _structural_diff 只比 (id, role) → 返回 None → 渲染跳过
   → 旧 ToolCallCard 仍在注册表，reg_key 仍为 PRE_FIX
7. 工具执行完成 → 结果携带 POST_FIX block_key
8. 绑定时 POST_FIX ≠ PRE_FIX → 匹配失败 → 工具结果独立显示
```

### 诊断日志验证（2026-05-03 实测）

已观察到：
- **绑定失败**：`block_key=5906056:0:002cd65a` 不在注册表（message_id 5906056 vs 注册表最小 5906161）
  - 这是**跨轮次遗留**问题，ToolCallCard 已不在可见区域
- **7 个绑定成功**：全部 `matched_by=block_key`，说明 block_key 机制在 ToolCallCard 存在时正常
- **AutoFix 导致 block_key 变化**：尚未在本次日志中观察到（需要触发含 AutoFix 的工具调用场景）

### 修复方案

**A. block_key 稳定性（根治，推荐 A1）**

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A1（推荐） | `stamp_code_blocks` 对同一 message_id:block_index 保持 block_key 不变。如果缓存中已有该位置的 block_key，保留原值，只更新 code_fp | 绑定不断，ToolCallCard 不需要重新注册 | block_key 不再精确反映内容指纹 |
| A2 | `block_key` 公式改为 `f"{message_id}:{code_index}"`，不含 code_fp | 最简单 | 丧失代码内容指纹区分能力，同位置不同内容无法区分 |
| A3 | ToolCallCard 同时注册 PRE_FIX 和 POST_FIX | — | 不可行，无法预知 POST_FIX |

**B. 渲染跳过修复（与 A 互补）**

`_structural_diff` 返回 None 时，额外检查 AI 消息代码块 block_key 是否变化：
- 如果变化，触发局部更新（只更新代码块内容变化的气泡）
- ToolCallCard 会用新 block_key 重新注册，绑定不会断

**C. 跨轮次遗留结果（独立问题）**

`block_key=5906056` 不在注册表是因为对应 ToolCallCard 已不在可见气泡中：
- 方案 C1：忽略（当前行为，工具结果独立显示）
- 方案 C2：提示用户"有历史工具结果未绑定"
- 建议：先 C1，低优先级

# 七、风险与边界

1. **NVirtualList 虚拟滚动** — 离屏消息 DOM 被回收后，JS 查询返回的元素数量可能少于实际消息数。缓存中有但 DOM 中没有的消息，保留缓存不删除（可能只是暂时离屏） ✅ 已处理
2. **JS 返回数据量** — 全量模式返回 ~10.5MB JSON，`execute_script` 实测可承受。增量模式下通常只返回 ~50KB ✅ 已验证
3. **message_id 缺失** — 部分消息没有 `data-message-id`，当前用 fallback hash（role+timestamp+preview 的 MD5 前 8 位），增量比对时用 `__idx_{i}` 兜底 ✅ 已处理
4. **fixing 过程中的缓存一致性** — AutoFix 展开代码块后，状态机驱动 `cache.invalidate_message(ai_msg_id)` 强制下次重新提取 ✅ 已处理
5. **工具结果提前渲染的时序** — `tool_result_ready_signal` 在工具线程 emit，UI 在主线程处理，需确保 ToolCallCard 已经渲染完成 ⚠️ 待实施时注意
6. **向后兼容** — 保留 `get_chat_content()` 原始接口作为 fallback，增量方法异常时降级到全量 ✅ 已实现

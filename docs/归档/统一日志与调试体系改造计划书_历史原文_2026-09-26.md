# 统一日志与调试体系改造计划书

> 最后编辑时间：2026-04-21
> 状态：实施中（阶段A-D已完成，E部分完成，F未开始）
> 适用范围：GUI 客户端、Worker、本地/远程日志链路、运行日志面板、API 模式调试、工具闭环调试、UI 渲染调试
> 用途：用于指导后续 AI 或工程师按阶段实施统一日志与调试体系改造，提升问题定位效率，避免继续用零散 print/status_signal 进行临时排查。

---

# 一、背景与问题

当前系统在调试时存在以下典型问题：

```md
1. 不同层的日志分散在不同通道
2. 有些日志只在 worker 端可见
3. 有些日志只在 GUI 进程 stdout 可见
4. 有些日志只在运行日志面板可见
5. print / logger / status_signal / server_log_signal 并存，口径不统一
6. 缺少 trace_id / round_id，难以串联一次完整请求
7. 流式 chunk 日志噪声过高，淹没关键信息
8. UI 调试信息无法稳定进入运行日志面板
9. AI 协作调试时，经常无法确认自己看到的是哪一端日志
10. 每次排查都需要临时插桩，且插桩很难复用
```

这些问题会直接导致：

```md
- 问题定位效率低
- 调试结论不稳定，容易误判
- AI 协作时上下文难以共享
- 排查严重依赖人工记忆系统结构
- 临时探针越插越乱，后续难以清理
```

因此，需要建立一套统一的日志与调试体系，使后续 AI 在排查问题时能稳定获取：

```md
谁发出的消息
消息经过了哪一层
每一层看到的状态是什么
同一次请求的日志如何串起来
UI 端最终是否收到并渲染
```

---

# 二、目标

本计划的目标不是“增加更多日志”，而是建立**统一、可过滤、可追踪、可面板展示、可文件落盘**的调试体系。

## 2.1 第一层目标：统一日志通道

让 GUI、Worker、远程链路、API Source、工具闭环、页面渲染等模块，尽量通过统一 logging 体系输出，而不是继续依赖裸 print。

## 2.2 第二层目标：统一调试入口

建立统一的 probe / trace 机制，使后续 AI 不再需要大量手写临时 print，而是可以按标签、模块、trace_id 精确插桩。

## 2.3 第三层目标：统一可见性

让以下信息在排查时都可被稳定查看：

```md
- 运行日志面板可见
- 本地日志文件可见
- 必要时远程回传可见
- 可按 trace_id / conversation_id / round_id 检索
```

## 2.4 第四层目标：控制噪声

避免流式 chunk、RPC 桥接等高频日志淹没真正需要关注的问题。

---

# 三、核心设计原则

## 3.1 禁止继续扩大 print 体系

后续新增调试信息原则上应优先走 logging / probe，而不是 print。

## 3.2 调试输出必须支持开关

所有高噪日志、细粒度探针都必须支持配置开关，不能常驻污染正常运行。

## 3.3 日志必须分层但可汇总

需要同时保留：

```md
- UI 侧日志
- Worker 侧日志
- RPC/远程链路日志
- 面板可见日志
```

但这些日志在需要时应可通过 trace_id 汇总关联。

## 3.4 不要把运行日志面板当成唯一日志源

运行日志面板适合快速观察，但不能替代持久化日志文件。

## 3.5 调试体系必须服务 AI 协作

日志内容要尽量结构化，使 AI 能快速判断：

```md
- 当前在哪一端
- 当前是哪一次请求
- 当前处于哪一个 round_state
- 当前渲染/工具链/流式链路是否收口
```

---

# 四、建议的整体架构

建议分四层建设：

```md
L1：统一 logging 基础设施
L2：统一面板输出通道
L3：全链路 trace / round 标识
L4：统一 probe（调试探针）机制
```

## 阶段 C：建立全链路 trace_id / round_id 机制

### 目标

让一次请求可以在 UI → Worker → API Source → Tool Loop → Finalized → UI Render 的链路中被串起来。

### 建议新增字段

```md
trace_id
conversation_id
round_id
stream_id
client_id
side
thread_name
```

### 建议接入点

#### API 发送入口

在 `api_send(...)` 或相应入口生成：

```python
trace_id = ...
round_id = ...
```

#### 向后传递的关键链路

```md
ChatPage -> Worker -> APISource -> ToolConversationLoop -> messages_signal / round_state_signal -> UI Render
```

### 至少要做的事

```md
[√] 每次发送消息生成 trace_id
[√] round_state 相关日志带上 round_id
[√] stream 相关日志带上 stream_id
[√] tool loop 相关日志带上 selected_protocol / loop_count
[√] UI render 日志带上 trace_id / round_id
```

### 阶段完成判定

```md
[√] 任意一次请求都能通过 trace_id 串起完整链路
[√] AI 能据此判断问题在哪一层中断
```

## 阶段 D：建立统一 probe（调试探针）机制

### 目标

不再每次排查都临时手写 print；改为统一、可开关、可过滤的 probe 输出。

### 建议新增

```md
app/core/debug/probe.py
```

### 建议接口

```python
def probe(tag: str, level: str = "debug", **kwargs): ...
```

### 使用方式示例

```python
probe(
    "api_round_state",
    side="worker",
    trace_id=trace_id,
    state="detecting_tools",
    conversation_id=conversation_id,
)

probe(
    "chatpage_finalized_before_render",
    side="ui",
    trace_id=trace_id,
    cached_count=len(messages),
    last_role=role,
)
```

### probe 应支持

```md
[√] 写入 logging.debug/info
[√] 自动附加 trace_id / module / thread 等上下文
[√] 按 tag 过滤
[√] 按 side 过滤
[√] 按配置开关启停
[√] 可选是否同步显示到运行日志面板
```

### 阶段完成判定

```md
[√] 以后新增调试点优先使用 probe，而不是裸 print
[√] AI 可以按 tag 指导插桩
```

---

## 阶段 E：建立日志级别与噪声控制策略

### 目标

将高频低价值日志降噪，避免影响问题定位。

### 推荐策略

#### 流式链路

```md
STARTED / COMPLETED / ERROR -> INFO
chunk 级 token/block 日志 -> DEBUG 或默认关闭
chunk 桥接转发 -> DEBUG 或 TRACE
```

#### RPC / SignalBridge 链路

```md
请求发起/结束/失败 -> INFO
每条小块转发 -> DEBUG 或默认关闭
```

#### 工具闭环

```md
候选收集 / 协议选择 / 工具执行开始结束 / finalized -> INFO
中间细碎 payload -> DEBUG
```

### 至少要做的事

```md
[√] 为流式日志单独提供开关
[√] 为 RPC 转发日志单独提供开关
[√] 为 probe tag 提供过滤配置
[√] 为运行日志面板提供"仅显示重要日志"能力
```

### 阶段完成判定

```md
[√] 默认运行时日志噪声可控
[√] 打开 debug 后又能获取足够细节
```

# 六、推荐实施顺序

严格建议按以下顺序推进：

```md
阶段 A：统一 logging 基础设施
阶段 B：运行日志面板接 logging handler
阶段 C：trace_id / round_id 全链路接线
阶段 D：统一 probe 机制
阶段 E：噪声控制与 debug 开关
阶段 F：调试视图增强
```

不要反过来先做调试页面，而不先统一底层日志。

---

# 七、首轮最小实施集（推荐优先）

如果当前资源有限，建议第一轮只先完成以下 6 项：

```md
[√] 新增 log_manager，统一 logging 初始化
[√] UI / Worker 各自落盘到日志文件
[√] RuntimeLogPanel 接 logging handler
[√] API 发送主链生成 trace_id
[√] 新增 probe() 工具函数
[√] 流式 chunk / SignalBridge 高频日志支持开关
```

做完这 6 项，就能明显缓解“AI 看不到关键日志”的问题。

---

# 八、实施边界与暂不处理项

为了不污染当前业务修复节奏，第一轮不建议同时做以下事情：

```md
[ ] 不要同时重构业务状态机
[ ] 不要同时重构消息存储结构
[ ] 不要把所有旧 print 一次性全量替换
[ ] 不要同时重构 MainWindow 全部信号系统
[ ] 不要第一轮就做复杂调试页面
```

建议优先做“新体系搭起来”，然后逐步迁移旧日志。

# 十一、结论

未来若想彻底解决“AI 想看日志却没有日志”的问题，不能继续依赖零散 print 和临时 signal 绕行。

必须逐步建立：

```md
统一 logging
+ 统一面板接入
+ 全链路 trace_id
+ 统一 probe
+ 可配置降噪
```

严格按本计划分阶段推进，可以在不大幅污染当前业务修复工作的前提下，逐步建立稳定的调试基础设施，显著提升 AI 与工程师协作排查效率。

无上下文浏览器 Profile 计划书

将某个 AI 网页对话作为"近似 stateless"的模型后端使用。每一轮请求前由项目侧编译完整上下文包并发送；每一轮完成后采集本轮网页回复，并尽量不依赖网页历史上下文继续推理。浏览器模式负责主力推理，API 模式负责工程副驾。

1. 背景与目标

🔑 API 模式

优点：完全自主可控、可并发、上下文精确、结构化协议稳定。

缺点：成本高，频繁调用时产生较大账单压力。

🌐 浏览器模式

优点：可调用网页端顶级模型，推理质量上限高，近似不限量使用。

缺点：上下文托管在网页端，项目无法完全控制；网页 UI 变化影响稳定性；天然不适合并发。

核心目标：引入无上下文浏览器 Profile——将 AI 网页对话作为"近似 stateless"的模型后端。Data-Bridge 不把网页历史当作可信上下文来源，真正的上下文事实保存在本地，由项目侧在每轮请求前重新组织。

最终效果

  • 浏览器模式负责主要智能推理、复杂分析、开发主流程与高质量生成。
  • API 模式负责可并发的辅助任务、严格结构化处理、工具调度胶水、校验修复和浏览器异常时的工程兜底。
  • 上层业务只关心统一的 Profile 调用结果，不关心底层来自 API 还是浏览器网页。
  • 设置页只负责 Profile 配置和 fallback 配置的增删改；每个本地对话可以选择自己的 Profile 或 Chain。

2. 核心原则

1. 项目侧持有上下文事实

浏览器网页只作为推理执行器，不作为可信上下文数据库。历史消息、工具结果、任务状态、知识库摘要都由 Data-Bridge 侧维护。

2. 每轮请求全量自描述

每次发给浏览器网页的 prompt 必须包含完成本轮任务所需的系统规则、任务目标、必要历史、输入数据和输出要求。不依赖网页端上一轮对话记忆。

3. 浏览器 Profile 纳入统一配置与调用

浏览器源不应成为独立分支逻辑，而应实现与 API Profile 相同的运行时调用入口。成本、延迟、可靠性、并发能力由 Profile 元数据描述。

4. 对话选择和配置管理分离

设置页负责管理 Profile 与 Chain。对话负责选择"本对话使用哪个 Profile/Chain"。全局 api_mode_usage 只作为未选择时的默认兜底。

5. 串行能力显式建模

浏览器 Profile 默认 supports_parallel = false。通过任务队列管理吞吐，不在上层假装它具备 API 一样的并发能力。

6. API 是工程副驾，不是默认主脑

网页自动化、输出解析、超时、风控、页面结构变化都必须被视为正常故障类型。API 的价值在于补浏览器短板：并发、结构化、小模型快速处理、工具调用编排、结果校验。

7. 浏览器源只能通过网页消息结构通信

浏览器源不是可自由收发 JSON RPC 的后端，它只能通过网页聊天输入框发送一段文本或 Markdown。网页返回也不是原始协议包，而是渲染后的 DOM 消息树。真实协议是"发送可渲染 prompt，读取 DOM 渲染结果，再恢复成标准消息"。

8. 不猜 DOM

浏览器交互必须优先依据 docs/dom、docs/page_outer.html 和 docs/GoamzAI平台智能化方案.md 中的 DOM 契约。截图只能辅助理解，不作为选择器依据。新建对话、命名对话、选择模型等隐藏栏能力，后续必须基于真实 DOM 证据实现。

3.2 StatelessBrowserProfile 流程

无上下文浏览器 Profile 的职责：

  1. 接收统一的 ModelRequest。
  2. 调用 ContextCompiler 生成完整 prompt。
  3. 调用 BrowserPromptEnvelope 将请求包装成网页聊天框可发送的文本或 Markdown。
  4. 驱动浏览器进入指定 AI 网页对话；当前主要通过 GoAmzAI 左侧会话标题定位目标对话。
  5. 清理或隔离当前网页对话状态。
  6. 输入完整 prompt。
  7. 在 GoAmzAI 生成期间，通过浏览器模式 transient 解析链路采集中间态 segments，只刷新 UI，不提前落库。
  8. 生成稳定后，通过现有浏览器消息同步链路采集本轮回复，而不是另写简化版 DOM 解析器。
  9. 在需要时交给 Optional StructuredExtractor 做 JSON/XML 等结构化提取。

3.3 ContextCompiler 数据

把项目侧状态编译成浏览器网页可理解的完整请求包。推荐 prompt 结构：

你是 Data-Bridge 的一个近似无上下文推理后端。
本次请求必须只依据下方输入完成任务，不要依赖任何网页历史对话。

<system_rules>...</system_rules>
<task>...</task>
<context_summary>...</context_summary>
<necessary_history>...</necessary_history>
<input_payload>...</input_payload>
<output_contract>
普通任务：请直接输出自然语言、Markdown、代码块或表格。
结构化任务：请额外把 JSON 放入 ```json fenced block。
</output_contract>

关键要求：历史不直接全量塞入，优先使用项目侧摘要与必要片段；普通任务不要强迫网页 AI 只输出 JSON；prompt 需要携带 request_id；prompt 最终必须能降级为一段网页输入框可粘贴的纯文本或 Markdown。

3.4 BrowserPromptEnvelope 流程

负责把标准请求包转换成网页聊天框可发送的单段消息。设计要求：

  • 使用明显的边界标签包裹各区域，例如 <system_rules>、<task>、<input_payload>、<output_contract>。
  • 首尾携带 request_id，并要求模型在输出中尽量回显同一个 request_id。
  • 避免依赖网页端隐藏 metadata，因为浏览器源只能发送可见文本。
  • 对大上下文做摘要和片段裁剪，保证一次粘贴可被网页输入框接受。
  • 对代码、JSON、日志等内容使用 Markdown fenced code block，降低网页富文本编辑器误解析概率。

3.5 BrowserConversationReset 核心

负责在每轮发送前把网页对话恢复到近似无上下文状态。必须真实操作网页 UI。

⚠️ 重要约束："清空"按钮只有在消息窗口置底后才会出现。reset 流程必须先滚动消息容器到底部，再查找按钮。不能直接在页面顶部或中间状态查找"清空"，否则会误判按钮缺失。

建议定位策略：

  1. 定位消息滚动容器，例如 .n-scrollbar-container / .n-scrollbar-content。
  2. 将消息窗口滚动到底部，并等待底部工具区渲染完成。
  3. 首选语义定位：查找可点击 button，其 .n-button__content 文本精确等于 清空。
  4. 辅助特征：按钮包含 n-button--tiny-type、n-button--ghost、clickable。
  5. 避免只依赖 data-v-* 属性，因为 Vue scoped attribute 可能随构建变化。
  6. 点击前记录当前最后一个 chat-item[data-message-id]，点击后等待旧消息消失。
  7. 若网页弹出确认框，适配器必须显式确认。
  8. 清空失败时不得发送本轮 prompt，应返回 reset_failed，由调度器决定重试、换浏览器 Profile 或 API takeover。

3.6 复用现有浏览器消息同步链路 核心

当前浏览器模式已具备较完整的消息解析和 UI 绑定能力。browser_stateless 应复用这些能力，它新增的是"每轮请求前清空/隔离网页上下文、发送完整 prompt、排队串行调用、按对话选择 Profile"的外层调度能力。

当前实现已复用的链路：

  • 最终稳定回复：scan_and_fix_last_message() 后调用 get_chat_content_incremental(transient_last_ai=False)，保留结构化 segments。
  • 生成中回复：wait_until_idle(progress_callback=...) 期间调用 extract_latest_ai_response(transient=True)，使用浏览器 transient parser 形成临时 segments。
  • API 对话落库：最终回复通过 append_assistant_message(..., segments=..., raw_content=...) 写入本地上下文。
  • 临时刷新：transient 消息只通过 messages_signal 推给 UI，不提前写入本地上下文。

GoAmzAI 可观察 DOM 形态：

.chat-item[data-message-id][data-message-ai]
  .content / .chat-text / .aa-html
    .node-slot[data-node-index][data-node-type]

提取规则：以 data-message-id 作为浏览器侧消息 ID；以 data-message-ai="true" 识别 AI 回复；按 data-node-index 升序恢复块顺序；根据 data-node-type 恢复块语义（paragraph / heading / list / code_block / blockquote / thematic_break）。

3.7 对话级 Profile 选择与 ProfileRouter 核心

运行时选择顺序：① 当前本地对话的 model_usage → ② 全局 api_mode_usage → ③ 默认 API Profile。

model_usage 支持两种形式：{"type": "profile", "ref": "browser_web_primary"} 或 {"type": "chain", "ref": "primary_browser_then_api"}。

API Profile — 并发强、结构化高、可控性高，但成本高、模型上限受配额限制
浏览器 Profile — 推理质量高、模型上限高、成本极低，但并发弱、可控性中低

3.8 统一上游事件层 下一步

API Profile 和浏览器 Profile 不应长期在 API 模式内部走两套语义。

当前临时状态：API Profile 通过 WorkerStreamBridge 输出 API stream chunk/status；浏览器 Profile 通过 WorkerBrowserStatelessBridge 模拟 started/completed，并额外推送 transient messages。UI 可以工作，但 worker 层仍需要知道"这是 API 流"还是"浏览器 DOM 观察"。

目标状态：

class UpstreamEvent:
    event: str  # started | delta | structured | completed | failed | diagnostic
    conversation_id: str
    request_id: str
    profile_key: str
    text_delta: str
    accumulated_text: str
    segments: list
    raw_message: dict | None
    diagnostics: dict

统一后：API token 流转换成 delta / completed；浏览器 transient DOM 观察转换成 structured；浏览器稳定回复转换成 completed，携带最终 segments；fallback chain 只关心事件和错误，不关心底层是 HTTP API 还是网页；UI、上下文、守护进程、工具闭环共用同一个上游事件消费口。

多个任务提交到同一浏览器 Profile 时按序执行；超时任务可以释放锁，不阻塞后续任务；失败任务有明确错误类型与诊断日志；主任务默认进入浏览器队列，API 接管必须记录原因。

Phase 415%
GoAmzAI 对话控制能力

基于 docs/dom、docs/page_outer.html 或新的 DOM 样本确认隐藏栏结构；支持新建网页对话；支持设置网页对话名称；支持选择网页模型；支持配置上下文携带数；支持打开高级设置并写入必要字段；明确哪些能力只属于浏览器模式，哪些在 API 模式下不需要保留。

验收

不靠截图猜选择器；新建对话、命名、选择模型、配置上下文携带数均有 DOM 契约或测试证据；API 模式把网页作为上游源时，不暴露无意义的网页消息操作。

Phase 535%
稳定性与观测

增加页面状态探测：未登录、页面加载中、输入框不可用、生成中、生成失败；增加清空按钮状态探测；增加 DOM 选择器版本化与备用选择器；增加截图或 HTML 片段诊断开关；记录每轮 prompt 摘要、响应摘要、耗时、重试次数、API assist/takeover 原因；记录统一上游事件；建立小型回归用例集。

验收

页面结构轻微变化时有备用路径或明确报错；出现卡死时能通过日志定位在哪个阶段失败；能统计浏览器 Profile 的成功率、平均耗时、主力任务占比和 API 辅助次数。

Phase 60%
多浏览器 Profile 扩展

支持多个浏览器账号或多个隔离浏览器数据目录；每个浏览器 Profile 独立锁、独立队列、独立健康状态；调度器按健康状态和队列长度选择浏览器 Profile；对高风险网页源设置冷却时间和请求频率上限。

验收

两个浏览器 Profile 可以并行处理两个队列；单个浏览器 Profile 异常不会影响其他 Profile；调度器能避开不健康 Profile。

5. 主力任务与 API 辅助任务

🌐 浏览器模式主力任务

  • 开发主流程中的复杂分析、架构判断、代码生成与方案设计
  • 需要顶级模型能力的长上下文推理
  • 高质量文档、计划书、审查意见、产品方案、调试判断
  • 需要反复推敲的主对话协作
  • 可排队但质量优先的任务
  • 需要保留 Markdown、代码块、富文本结构的回复

🔑 API 模式辅助任务

  • 小而快的结构化转换，例如 JSON 修复、字段抽取、格式校验
  • 多路并发的轻量任务，例如批量分类、批量摘要、候选项初筛
  • 工具调用参数生成、工具结果压缩、协议桥接
  • 浏览器网页不可用、队列过长或用户明确要求立即响应时的接管
  • 不适合进入网页端的敏感任务

⚠️ 谨慎进入浏览器模式的任务

  • 涉及私钥、账号、付款、内部敏感数据的任务
  • 必须毫秒级响应或强并发的任务
  • 输出协议不可失败且无法二次修复的任务
  • 需要完全自主控制推理上下文和审计链路的任务

6. 风险与对策

网页 UI 变化
影响：自动化失效
对策：选择器版本化、页面状态探测、失败诊断截图
输出格式不稳定
影响：结构化提取失败
对策：fenced code block、解析修复、API assist；保留原始回复
浏览器无法并发
影响：队列积压
对策：显式队列、优先级、API 分担轻量任务、多 Profile 扩展
清空按钮定位失败
影响：无法进入无上下文状态
对策：按文本定位为主、class/图标特征为辅、失败时停止发送并记录诊断
网页端上下文残留
影响：结果受污染
对策：每轮真实点击清空或新建对话、清空后校验、完整 prompt、request_id 校验
账号级记忆或网页策略影响
影响：不完全 stateless
对策：在文档和配置中标记为"近似 stateless"，敏感任务转 API 或本地模型
风控或限流
影响：任务失败
对策：请求频率限制、冷却时间、退避重试、健康状态降级
隐私与合规
影响：数据泄露风险
对策：敏感任务强制 API 或本地模型，不进入浏览器 Profile
重写浏览器解析链路
影响：代码块、工具卡片、执行入口

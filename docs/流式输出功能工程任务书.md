# 流式输出功能工程任务书

> 历史阶段记录（2026-09-05 整理）：以下原文用于追溯当时的设计、实现与验证；当前能力见[项目状态](当前项目状态.md)，当前测试命令见[测试说明](../tests/README.md)。

## 1. 目标与背景

现状：
- 当前API模式对话接口属于“闪出式”回复，用户无法感知AI回复生成过程中的状态，交互体验不流畅。
- 现有后端有异步流式调用接口（`send_message_stream`），但未被完整链路调用或逐步推送给前端。
- 前端消息渲染基于“全消息列表替换”，不支持流式增量渲染及“AI输入中”状态动画。

目标：
- 实现API模式对话的异步流式输出，前端能逐字逐块展示AI回复，明显提升交互流畅度和用户体验。
- 提供“AI正在输入”等中间状态反馈，减少用户空白等待焦虑。
- 采用模块化设计，避免现有大文件体量无序增长。

## 2. 核心用户需求

1. 后端支持
   - 异步支持流式调用，AI生成回复时可逐步推送内容给客户端。
   - 流式数据需包含初始状态通知、中间增量数据和结束信号。
   - 发送单个消息增量或文本片段，而非全量消息列表。

2. 消息协议
   - 流式消息应设计为统一格式，每条消息包含唯一ID、内容增量、状态字段。
   - 支持“部分完成”和“全部完成”标志，允许客户端增量拼接及重试。

3. 前端交互
   - 实时接收并增量渲染AI回复内容，避免全量刷新消息面板导致的闪烁。
   - 实时展示“AI正在输入”动画或文字提示。
   - 流结束后自动转换为标准对话状态，允许用户继续或中断交互。

4. 异常处理
   - 流传输异常应明确通知前端，触发错误提示。
   - 支持流中断恢复或重连机制。

## 3. 软件架构与实现规范

3.1 代码结构原则
- 小文件单一职责，避免大文件膨胀。
- 流式功能相关代码拆分至api_stream_models.py、api_stream_state.py、api_stream_handler.py等文件。
- 命名遵循蛇形命名，同目录下统一前缀方便检索。
- 流式调用与信号管理独立，保护老接口不受影响。

3.2 技术栈及接口建议
- 后端异步接口基于已有send_message_stream异步迭代器。
- API通信层支持WebSocket或SSE协议流式通信。
- 前端使用信号槽或事件订阅模式实时渲染流式数据。

## 4. 任务拆解示例

| 模块/文件名             | 功能描述                               | 所属目录           |
|-------------------------|---------------------------------------|--------------------|
| api_stream_models.py     | 定义流式消息结构体和状态枚举           | app/core/api/       |
| api_stream_state.py      | 流式对话状态管理，缓存增量文本         | app/core/api/       |
| api_stream_handler.py    | 连接APISource与流式信号的转换层       | app/core/api/       |
| worker_api_stream.py     | Worker线程异步流式调用和信号广播接口    | app/core/worker/    |
| chat_page_stream.py      | ChatPage流式接口封装，流式消息订阅处理  | app/ui/pages/chat/  |
| message_area_stream.py   | 增量渲染消息区，支持拼接刷新           | app/ui/pages/chat/  |
| chat_bubble_stream.py    | 流式聊天气泡，实现增量文本追加和动画    | app/ui/components/  |

## 5. 验收标准

- 流式异步接口逐块yield文本片段，客户端增量渲染。
- UI显示流开始“AI正在输入”动画，结束自动切换状态。
- 消息显示无闪烁，增量追加自然流畅。
- 异常通知前端，支持中断恢复。
- 新文件体量均控制在80-300行，小文件单职责。
- 命名统一，易于AI检索维护。
- 保持同步接口兼容，API模式选择性启用流式。

# 七、联调方案

1. **环境准备**
   - 后端部署已完成流式接口，启用相关配置
   - 前端开发环境支持信号槽或事件订阅机制
   - 调试工具（如浏览器开发者工具、后端日志）就位

2. **接口联通测试**
   - 逐步调用`api_send`接口，分别传`stream=True/False`参数
   - 观察后端是否正确触发`start_stream`，信号是否正确发出
   - 前端是否能监听到`api_stream_chunk_signal` 和 `api_stream_status_signal`

3. **UI渲染联动**
   - 前端确认消息区`ChatPageStreamManager`、`MessageAreaStreamManager` 能正确增量渲染
   - 验证流开始、结束动画及提示状态
   - 重复发流测试，测试多次连续流处理

4. **异常及边界处理**
   - 模拟API异常断流，验证前端异常提示与恢复能力
   - 网络慢、包丢弃等极端情况测试

5. **性能监控**
   - 测试全量和流式消息对界面性能影响
   - 检查内存泄漏、信号重复绑定、UI卡顿等问题


# 八、后续提升与扩展建议

1. **流式消息重连机制**
   - 实现基于消息ID的断点续传和重试逻辑
   - 优化用户体验，减少空白等待

2. **更细粒度的流式分块格式**
   - 支持token级或按句分割流式增量，提升显示精细度

3. **多模型流式输出管理**
   - 支持多个模型同时输出流，合并渲染能力设计

4. **前端流式动画优化**
   - 加入打字机效果、渐变高亮、交互性提示

5. **权限及访问控制**
   - 流式数据权限鉴权与安全管控

6. **日志与调试工具**
   - 设计专门的流式调试面板，实时监控流状态与数据包

7. **跨平台适配**
   - 优化移动端流式响应体验
